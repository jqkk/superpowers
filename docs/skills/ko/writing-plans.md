# writing-plans — 구현 계획 작성

> 원문: [`skills/writing-plans/SKILL.md`](../../../skills/writing-plans/SKILL.md)
> 트리거(원문 유지): `Use when you have a spec or requirements for a multi-step task, before touching code`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

이 코드베이스도 이 스펙도 **본 적 없는** 엔지니어를 위해 구현 계획을 쓴다. 정확한 인터페이스와 정확한 테스트만 알면 그 프로젝트 언어로 관용적인 코드를 쓰고, 계획이 열어 둔 곳에서는 합리적인 선택을 할 사람이라고 가정한다. 그들이 알 수 없는 것은 **내가 무엇을 결정했는지**다: 어떤 파일, 어떤 이름과 시그니처, 스펙의 어떤 값, 각 태스크를 증명하는 어떤 테스트. 그것들을 문서화한다. 계획 전체를 한입 크기 태스크로 준다. DRY. YAGNI. TDD. 잦은 커밋.

**시작할 때 선언:** "writing-plans 스킬을 사용해 구현 계획을 작성합니다."

**맥락:** 격리된 워크트리에서 작업 중이라면, 실행 시점에 `superpowers:using-git-worktrees` 스킬로 만들어졌어야 한다.

**계획 저장 위치:** `docs/superpowers/plans/YYYY-MM-DD-<기능명>.md`
- (계획 위치에 대한 사용자 선호가 이 기본값을 덮어쓴다)

## 범위 점검

스펙이 여러 독립 서브시스템을 다룬다면 브레인스토밍 단계에서 서브 프로젝트 스펙으로 쪼개졌어야 한다. 그러지 않았다면 서브시스템당 하나씩 별도 계획으로 쪼개자고 제안한다. 각 계획은 그 자체로 동작하고 테스트 가능한 소프트웨어를 만들어내야 한다.

## 파일 구조

태스크를 정의하기 전에 어떤 파일이 생성·수정될지, 각각 무엇을 책임지는지 먼저 그린다. 분해 결정이 여기서 확정된다.

- 경계가 명확하고 인터페이스가 잘 정의된 단위로 설계한다. 각 파일은 하나의 명확한 책임을 가진다
- 한 번에 컨텍스트에 담을 수 있는 코드에 대해 가장 잘 추론하게 되고, 파일이 집중되어 있을 때 편집이 더 신뢰할 만하다. 너무 많은 일을 하는 큰 파일보다 작고 집중된 파일을 선호한다
- 함께 바뀌는 파일은 함께 둔다. 기술 계층이 아니라 책임으로 쪼갠다
- 기존 코드베이스에서는 확립된 패턴을 따른다. 코드베이스가 큰 파일을 쓴다면 일방적으로 재구성하지 않되, 수정 중인 파일이 감당 못 할 만큼 커졌다면 분할을 계획에 포함하는 것은 합리적이다

이 구조가 태스크 분해에 정보를 준다. 각 태스크는 독립적으로 말이 되는 자족적 변경을 만들어야 한다.

## 태스크 크기 정하기

태스크란 **자기만의 테스트 사이클을 가지고, 새로운 리뷰어의 게이트를 받을 가치가 있는 가장 작은 단위**다. 태스크 경계를 그을 때: 셋업, 설정, 스캐폴딩, 문서화 단계는 그것을 필요로 하는 산출물의 태스크 안으로 접어 넣는다. 리뷰어가 한 태스크는 거절하고 옆 태스크는 승인하는 것이 의미 있는 곳에서만 쪼갠다. 각 태스크는 독립적으로 테스트 가능한 산출물로 끝난다.

## 스텝 세분화

**각 스텝은 확인 가능한 결과를 가진 하나의 행동:**
- "실패하는 테스트를 쓴다" — 스텝
- "실행해서 실패하는지 확인한다" — 스텝
- "테스트를 통과시킬 최소한의 코드를 구현한다" — 스텝
- "테스트를 실행해 통과하는지 확인한다" — 스텝
- "커밋한다" — 스텝

## 계획 문서 헤더

**모든 계획은 이 헤더로 시작해야 한다:**

````markdown
# [기능명] Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** [무엇을 만드는지 한 문장]

**Architecture:** [접근에 대해 2~3문장]

**Tech Stack:** [핵심 기술/라이브러리]

**Spec:** [이 계획이 구현하는 스펙/설계 문서 경로 — 계획은 스펙으로부터
논증하므로 스펙이 계획과 함께 이동한다. 실행자는 둘 다 읽는다]

## Global Constraints

[스펙의 프로젝트 전역 요구사항 — 버전 하한, 의존성 제한, 네이밍과
문구 규칙, 플랫폼 요구사항 — 한 줄씩, 정확한 값을 스펙에서 그대로 복사.
모든 태스크의 요구사항에 이 섹션이 암묵적으로 포함된다]

## Review Focus

[스펙이 암시하지만 어떤 태스크의 테스트도 검사하지 않는, 이 소프트웨어를
쓰는 사람을 가장 물 가능성이 높은 입력 종류 또는 실패 모드 다섯 가지 —
한 줄씩, 입력이나 조건과 합리적인 사람이 기대할 동작을 적고, 가능성이
높은 것부터. 스펙은 비전 문서다: 소프트웨어가 무엇을 해야 하는지를 말하지
무엇을 만나게 될지 전부 말하지 않으며, 어떤 입력에 대한 스펙의 침묵이 그
입력으로 프로그램이 깨져도 된다는 허가는 아니다. 스펙을 앞에 두고 이
목록을 여기 한 번 쓴다. 그다음 각 줄마다, 그것을 고정하는 테스트를 그
코드를 소유한 태스크에 그 태스크의 스텝 형식으로 추가한다]

---
````

## 태스크 구조

````markdown
### Task N: [컴포넌트명]

**Files:**
- Create: `exact/path/to/file.py`
- Modify: `exact/path/to/existing.py:123-145`
- Test: `tests/exact/path/to/test.py`

**Interfaces:**
- Consumes: [이 태스크가 앞선 태스크로부터 쓰는 것 — 정확한 시그니처]
- Produces: [이후 태스크가 의존하는 것 — 정확한 함수명, 파라미터와
  반환 타입. 태스크의 구현자는 자기 태스크만 본다. 이 블록이 이웃
  태스크가 쓰는 이름과 타입을 알게 되는 유일한 통로다]

- [ ] **Step 1: 실패하는 테스트를 쓴다**

```python
def test_specific_behavior():
    result = function(input)
    assert result == expected
```

- [ ] **Step 2: 테스트를 실행해 실패를 확인한다**

Run: `pytest tests/path/test.py::test_name -v`
Expected: FAIL with "function not defined"

- [ ] **Step 3: `exact/path/to/file.py`에 `function(input: InputType) -> ResultType`을 구현한다**

시그니처와 테스트가 선택의 여지를 남길 때(어떤 라이브러리 호출, 어떤
자료구조)에만 접근 방식을 한 줄로 적는다. 코드 블록은 그것들이 결정하지
않는 알고리즘에만 쓴다.

- [ ] **Step 4: 테스트를 실행해 통과를 확인한다**

Run: `pytest tests/path/test.py::test_name -v`
Expected: PASS

- [ ] **Step 5: 커밋**

```bash
git add tests/path/test.py src/path/file.py
git commit -m "feat: add specific feature"
```
````

## 스텝에 담기는 것

구현자가 그 스텝으로부터 **합리적인 것 정확히 하나**를 쓸 수 있으면 그 스텝은 완성이다. 요구사항은 그것이 전부다: 완전함이 아니라 모호하지 않음. 스텝의 종류마다 그것을 모호하지 않게 만드는 것만 담고, 그 이상은 담지 않는다:

- **테스트 스텝:** 테스트의 이름과 단언(assertion)을 코드로, 스펙의 정확한 값을 넣어서.
- **코드 스텝:** 정확한 시그니처(이름, 파라미터, 반환 타입), 그것이 위치할 파일, 스펙이 못 박은 구체적인 값. 본문은 구현자가 쓴다. 본문은 시그니처와 테스트가 결정하지 않는 알고리즘이거나 스펙이 고정한 정확한 문구일 때만 등장한다.
- **검증 스텝:** 실행할 명령과 통과를 의미하는 출력.
- **다른 태스크에 대한 참조:** 그 태스크의 Interfaces 블록이 무엇을 쓸지 말해 준다. 계획은 그 태스크의 코드를 반복하지 않는다.

계획은 **구현자가 혼자서는 내릴 수 없는 결정들의 집합**이다. 자기가 설명하는 코드보다 긴 계획은 계획 대신 코드를 써 버린 것이다. 아무것도 결정하지 않는 줄("TBD", "엣지 케이스를 처리", "적절한 검증을 추가", "위 내용에 대한 테스트를 작성", 어떤 태스크도 정의하지 않는 타입이나 함수)은 그 반대쪽 실패이며, 셀프 리뷰가 둘 다 잡아낸다.

## 셀프 리뷰

계획 전체를 쓴 뒤, 새로운 눈으로 스펙을 보고 계획을 스펙에 대조한다. 이것은 서브에이전트 파견이 아니라 직접 돌리는 체크리스트다.

**1. 스펙 커버리지:** 스펙의 각 섹션/요구사항을 훑는다. 그것을 구현하는 태스크를 짚을 수 있는가? 빠진 것을 나열한다.

**2. 스텝 스캔:** 모든 스텝은 구현자가 합리적인 것 정확히 하나를 쓸 수 있게 해야 하고, 어떤 스텝도 그 이상을 담아선 안 된다: 아무것도 결정하지 않는 줄은 빈틈이고, 시그니처와 테스트가 이미 결정하는 함수 본문은 받아쓰기다. 둘 다 고친다.

**3. 타입 일관성:** 후반 태스크에서 쓴 타입, 메서드 시그니처, 속성 이름이 앞선 태스크에서 정의한 것과 맞는가? Task 3에서 `clearLayers()`인데 Task 7에서 `clearFullLayers()`면 버그다.

**4. Review Focus:** 스펙이 암시하는 각 입력 종류나 실패 모드에 대해, 그것을 검사하는 테스트를 가진 태스크가 있는가? 사람을 물 가능성이 가장 높은 미커버 다섯 개가 Review Focus 섹션에 들어가고, 그 각 줄의 테스트는 해당 코드를 소유한 태스크에 추가된다. 섹션이 비어 있다는 것은 **확인했는데 없었다**는 뜻이지 확인을 건너뛰었다는 뜻이 아니다.

**5. 비례:** 계획의 길이를 스펙의 길이와 비교한다. 구현하는 스펙보다 몇 배나 긴 계획은 계획이 아니라 프로그램의 받아쓰기다. 코드 블록이 문서의 대부분이라면, 본문을 시그니처, 테스트 이름, 단언으로 바꾸고 각 스텝이 여전히 모호하지 않은지 확인한다.

문제를 찾으면 인라인으로 고친다. 재검토할 필요 없다 — 고치고 넘어간다. 태스크가 없는 스펙 요구사항을 찾으면 태스크를 추가한다.

## 실행 인계

계획을 저장하고 셀프 리뷰한 뒤, 사람 파트너가 읽을 수 있게 링크한다. 그들이 이미 실행 방식을 명시적으로 지정했다면, 계획이 그들이 원하는 것을 담았는지 검토·확인해 달라고 요청하고, 그 검토를 기다린 뒤 지정된 방식을 쓴다. 그렇지 않다면 계획을 검토하고 구현 전에 실행 방식을 골라 달라고 요청한다.

**실행 방식이 아직 지정되지 않았을 때:**

> **"계획이 완성되어 `docs/superpowers/plans/<파일명>.md`에 저장되었습니다. 계획을 검토해 주세요. 어떤 실행 방식을 선호하시나요?**
>
> - **Subagent-driven** — 태스크마다 새 서브에이전트가 구현하고 새 리뷰어가 검사한 뒤 다음으로 넘어가며, 마지막에 브랜치 전체 리뷰를 합니다. 가장 철저하지만, 태스크마다 그리고 리뷰마다 새 컨텍스트 비용이 듭니다.
> - **Native** — 제가 이 세션에서 모든 태스크를 이 하네스 방식대로 직접 구현하고, 마지막에 가장 유능한 모델의 새 리뷰어 하나가 브랜치 전체를 검사합니다. 가장 싸고 빠르지만, 마지막까지 독립적인 리뷰가 없습니다. 계획이 설계를 담고 있으므로 중간 티어 세션 모델로도 잘 돌아갑니다.
>
> **이 계획에는 <둘 중 하나>를 추천합니다. <계획에서 나온 한 문장: 태스크들이 서로의 인터페이스에 얼마나 의존하는지, 몇 개인지, 실수가 출시되면 얼마나 비싼지>이기 때문입니다. 계획이 원하시는 바를 담고 있나요? 그리고 어떤 방식으로 할까요?"**

**실행 방식이 이미 지정되었을 때:**

> **"계획이 완성되어 `docs/superpowers/plans/<파일명>.md`에 저장되었습니다. 계획을 검토해 주세요. 원하시는 바를 담고 있나요?"**

**Subagent-driven을 선택하면:**
- **필수 서브스킬:** superpowers:subagent-driven-development

**Native를 선택하면:**
- **필수 서브스킬:** superpowers:executing-plans
