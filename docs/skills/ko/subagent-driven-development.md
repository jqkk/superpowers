# subagent-driven-development — 서브에이전트 주도 개발 (SDD)

> 원문: [`skills/subagent-driven-development/SKILL.md`](../../../skills/subagent-driven-development/SKILL.md)
> 트리거(원문 유지): `Use when executing implementation plans with independent tasks in the current session`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

태스크마다 새 구현자 서브에이전트를 파견하고, 각 태스크 후에 태스크 리뷰(스펙 준수 + 코드 품질)를 하고, 마지막에 브랜치 전체에 대한 폭넓은 리뷰를 해서 계획을 실행한다.

**왜 서브에이전트인가:** 격리된 컨텍스트를 가진 전문 에이전트에게 태스크를 위임한다. 지시와 컨텍스트를 정밀하게 구성함으로써 그들이 집중을 유지하고 태스크에 성공하게 만든다. 그들은 **내 세션의 컨텍스트나 히스토리를 절대 상속받지 않는다** — 그들에게 필요한 것을 내가 정확히 구성해 준다. 이것은 내 컨텍스트도 조정 작업용으로 보존해 준다.

**핵심 원칙:** 태스크마다 새 서브에이전트 + 태스크 리뷰(스펙 + 품질) + 폭넓은 최종 리뷰 = 높은 품질, 빠른 반복

**서술:** 툴 호출 사이에는 짧은 한 줄까지만 — 원장과 툴 결과가 기록을 담당한다.

**연속 실행:** 태스크 사이에 사람 파트너에게 확인하려고 멈추지 않는다. 계획의 모든 태스크를 멈추지 않고 실행한다. 멈출 이유는 아래 네 가지 또는 전체 완료뿐이다. "계속할까요?" 프롬프트와 진행 요약은 그들의 시간을 낭비한다 — 계획을 실행해 달라고 했으니 실행하라.

**판정(Ruling)이지 정지가 아니다.** 실행 중인 계획은 사람을 기다리지 않는다. 충돌, 모호함, 계획 결함, 초과하겠다고 물었을 법한 상한 — 직접 결정한다. **스펙이 구속력 있는 권위이고, 계획은 그 논증이며, 둘 다 답하지 않는 것은 내 판단이 결정한다.** 모든 결정을 원장에 `Ruling: <무엇을 결정했는지> — <왜> — <틀렸을 때의 비용>`로 기록하고 계속 간다. 잘못된 판정은 파트너가 보고 되돌릴 수 있는 재작업 비용이지만, 질문 앞에 멈춰 선 세션은 그들의 하루 전체를 쓰고 아무것도 사지 못한다.

멈추는 것은 딱 네 가지다: 되돌릴 수 없거나 파괴적인 작업, 보안에 민감한 작업, 이 워크트리 밖으로 나가는 부수효과 중 통상 먼저 물어야 하는 것(머지, 공유 브랜치 푸시, 배포), 그리고 어떤 길도 추측일 만큼 망가진 계획. 이런 경우에는 멈추고 묻는다.

## 언제 쓰나

```
구현 계획이 있는가?
 ├─ 아니오 → 수동 실행 또는 브레인스토밍 먼저
 └─ 예 → 태스크가 대체로 독립적인가?
      ├─ 아니오(강하게 결합) → 수동 실행 또는 브레인스토밍 먼저
      └─ 예 → 파트너가 인라인을 골랐거나 서브에이전트 도구가 없는가?
           ├─ 예 → executing-plans
           └─ 아니오 → subagent-driven-development
```

**executing-plans(인라인)와의 비교:**
- 하나의 컨텍스트가 모든 태스크를 하는 대신, 태스크마다 새 서브에이전트(컨텍스트 오염 없음)
- 마지막에만 리뷰하는 대신, 태스크마다 리뷰(스펙 준수 + 코드 품질)
- 태스크마다, 리뷰마다 새 컨텍스트 비용이 든다. 인라인은 컨텍스트 하나 + 최종 리뷰어 하나
- 둘 다 이 세션에서 돌고, 같은 계획 워크스페이스와 원장을 공유하며, 태스크 사이에 멈추지 않는다

## 셋업

작업이 격리된 공간에서 일어나게 한다: superpowers:using-git-worktrees로 만들거나 기존 것을 확인한다. 사람 파트너의 명시적 동의 없이 main/master에서 구현을 시작하지 않는다.

대화 기억은 컴팩션을 견디지 못한다. 실제 세션에서 자기 위치를 잃은 컨트롤러가 **이미 완료된 태스크 전체를 재파견**한 사례가 있다 — 관찰된 것 중 가장 비싼 실패다. 진행 상황을 todo에만 두지 말고 원장 파일에 추적한다.

- 각 계획은 워크스페이스를 소유한다. 스킬 시작 시 이 스킬의 `bash scripts/sdd-workspace PLAN_FILE`을 **절대 경로로, 내가 실행 중인 작업 트리에서** 실행하면 계획의 git-ignore된 디렉터리(`<repo-root>/.superpowers/sdd/` 아래)를 출력한다. **이 계획의** 모든 산출물(원장, 브리프, 리포트, 리뷰 패키지)이 여기 산다. 다른 계획의 디렉터리는 절대 읽거나 쓰지 않는다
- `<workspace>/progress.md`에 이 계획의 원장이 있는지 확인한다. 있다면 다른 무엇보다 먼저 [`references/resuming.md`](../../../skills/subagent-driven-development/references/resuming.md)를 읽는다: 그것이 누구의 원장인지, 어디서 재개할지 알려준다
- 원장을 만들 때 첫 줄에 정체를 적는다: `# SDD ledger — plan: <계획 파일 경로>`
- **원장은 내 복구 지도다.** 거기 적힌 커밋은 내 컨텍스트가 그것을 만든 기억을 잃어도 git에 존재한다. 컴팩션 이후에는 내 기억보다 원장과 `git log`를 믿는다
- `git clean -fdx`는 워크스페이스를 파괴한다(git-ignore된 스크래치다). 그러면 `git log`에서 복구한다

계획을 한 번 읽고, 맥락과 Global Constraints를 기록하고, 태스크마다 todo를 만든다. 계획이 Spec을 지정하면 그것도 읽는다: 스펙은 계획이 논증하는 권위이고, 계획 내부의 충돌은 스펙에 비추어 해소된다. 닿을 수 있는 스펙이 없는 계획은 그 사실을 원장 노트로 남긴다 — 그 없이 내린 판정은 잠정적이다.

Task 1을 파견하기 전에 [`references/preflight.md`](../../../skills/subagent-driven-development/references/preflight.md)를 읽고 거기 기술된 충돌 스캔을 돌린다. 그 표와 판정은 원장에 들어간다.

## 모델 선택

비용을 아끼고 속도를 높이기 위해 각 역할을 감당할 수 있는 **가장 약한 모델**을 쓴다.

**기계적 구현 태스크**(독립 함수, 명확한 스펙, 1~2개 파일): 빠르고 싼 모델. 계획이 잘 명세되어 있으면 대부분의 구현 태스크는 기계적이다.

**통합과 판단 태스크**(다중 파일 조율, 패턴 매칭, 디버깅): 표준 모델.

**아키텍처와 설계 태스크**: 가장 유능한 모델. **최종 브랜치 전체 리뷰가 여기 해당한다** — 세션 기본값이 아니라 가장 유능한 모델로 파견한다.

**리뷰 태스크**: 같은 판단을 diff의 크기·복잡도·위험에 맞춰 적용한다. 작은 기계적 diff에는 가장 유능한 모델이 필요 없고, 미묘한 동시성 변경에는 필요하다. 작은 수정 diff의 범위 한정 재리뷰는 싸거나 중간 티어로.

**수정 루프 에스컬레이션(4~5라운드)**: 막힌 구현자보다 **최소 한 티어 위** 모델.

**서브에이전트를 파견할 때는 항상 모델을 명시적으로 지정한다.** 생략하면 내 세션 모델 — 보통 가장 유능하고 가장 비싼 — 을 상속하며, 이 절이 조용히 무력화된다.

**턴 수가 토큰 단가를 이긴다.** 실제 시간과 컨텍스트 비용은 서브에이전트가 몇 턴을 쓰느냐에 비례하며, 가장 싼 모델은 다단계 작업에서 일상적으로 2~3배의 턴을 쓴다 — 결국 더 비싸다. 리뷰어와 산문 설명으로 작업하는 구현자에게는 **중간 티어를 하한으로** 쓴다. 태스크의 계획 텍스트에 쓸 코드가 전부 들어 있다면 구현은 전사 + 테스트다. 그런 구현자에게는 가장 싼 티어를 쓴다. 단일 파일 기계적 수정도 가장 싼 티어.

**태스크 복잡도 신호(구현 태스크):**
- 완전한 스펙으로 1~2개 파일을 건드림 → 싼 모델
- 통합 고려사항이 있는 여러 파일 → 표준 모델
- 설계 판단이나 코드베이스 전반 이해 필요 → 가장 유능한 모델

## 태스크 루프

**같은 모양의 작은 작업:** 계획이 여러 파일에 걸쳐 같은 종류의 작은 편집을 여러 개 나열한다면, 그것들을 파견하기 전에 [`references/batching.md`](../../../skills/subagent-driven-development/references/batching.md)를 읽는다.

파견 프롬프트에 붙여넣는 모든 것과 서브에이전트가 되돌려 출력하는 모든 것은 세션이 끝날 때까지 내 컨텍스트에 남고 이후 모든 턴에서 다시 읽힌다. **산출물은 파일로 주고받는다.**

**파견된 서브에이전트 대기:** 짧은 타임아웃으로 대기 인터페이스를 폴링하지 않고, 조용한 무한 대기에 앉아 있지도 않는다. 로컬 작업(원장 갱신, 다음 리뷰 패키징, 리포트 읽기)이 있는 동안에는 계속 일한다. 자식의 결과는 알아서 도착한다. 정말로 할 일이 없을 때는 **경계가 있는 구간**(플랫폼이 허용하면 5~10분)으로 기다리고, 구간 사이에 상태 한 줄을 남기고 살아 있는 자식들을 대조한다: 목록을 뽑고, 보고 없이 끝난 것을 추적한다. 경계 있는 구간은 긴 대기의 효율을 거의 다 유지하면서, 막히거나 유실된 자식을 세션 끝이 아니라 몇 분 안에 알아채게 해준다.

### 1. 구현자를 파견한다

파견 전에 BASE(`git rev-parse HEAD`)를 기록한다 — 리뷰 패키지와 수정 라운드 diff에 필요하다.

- **태스크 브리프:** 구현자를 파견하기 전에 이 스킬의 `bash scripts/task-brief PLAN_FILE N`을 절대 경로로, 내가 실행 중인 작업 트리에서 실행한다. 태스크의 전체 텍스트를 고유한 이름의 파일로 추출하고 경로를 출력한다. **브리프가 요구사항의 단일 출처로 남도록** 파견을 구성한다. 파견에는 다음이 들어간다: (1) 이 태스크가 프로젝트에서 어디에 들어가는지 한 줄, (2) 브리프 경로 — "먼저 이것을 읽어라. 이것이 네 요구사항이며, 정확한 값을 그대로 쓴다"고 소개, (3) 브리프가 알 수 없는, 앞선 태스크의 인터페이스와 결정, (4) 브리프에서 내가 발견한 모호함에 대한 내 해소, (5) 리포트 파일 경로와 리포트 계약. **정확한 값(숫자, 매직 스트링, 시그니처, 테스트 케이스)은 브리프에만 나타난다.** 서브에이전트에게 계획 파일 전체를 읽게 하지 않는다
- **리포트 파일:** 구현자의 리포트 파일 이름을 브리프에 맞춰 짓고(브리프 `…/task-N-brief.md` → 리포트 `…/task-N-report.md`) 파견 프롬프트에 넣는다. 구현자는 전체 리포트를 거기 쓰고, 돌려주는 것은 상태, 커밋, 한 줄 테스트 요약, 우려뿐이다
- 파견 프롬프트는 **태스크 하나를 서술하지 세션 히스토리를 서술하지 않는다.** 누적된 이전 태스크 요약("Tasks 1-3 이후 상태")을 이후 파견에 붙여넣지 않는다 — 실제 세션의 파견이 42,000자에 달했는데 그중 99%가 붙여넣은 히스토리였다. 새 서브에이전트에게 필요한 것은 자기 태스크, 자기가 건드리는 인터페이스, 전역 제약뿐이다
- 파견은 **서브에이전트 금지 계약**을 담는다(구현자 템플릿에 들어 있다): 구현자는 서브에이전트를 파견하지 않는다 — 헬퍼도, 리뷰어는 더더욱. 리뷰는 리포트 이후 나로부터 온다. 실제 세션에서 작업자가 스폰한 리뷰어는 전부 컨트롤러가 어차피 파견한 태스크 리뷰를 중복했다 — 태스크당 리뷰 좌석 하나가 통째로 더 든 셈이다
- 앞선 태스크가 이 태스크가 건드리는 영역에 발견을 park해 뒀다면, 그 원장 항목에 대한 포인터를 파견에 담는다
- 파견 결과에서 구현자의 에이전트 식별자를 기록한다 — 수정 루프 1~3라운드가 이 에이전트를 재개한다
- **구현 서브에이전트를 병렬로 여러 개 파견하지 않는다**(충돌)

템플릿: [implementer-prompt.md](../../../skills/subagent-driven-development/implementer-prompt.md)

### 2. 리포트를 처리한다

구현자 서브에이전트는 네 가지 상태 중 하나를 보고한다. 각각 적절히 처리한다:

**DONE:** 리뷰 패키지를 생성하고(`bash scripts/review-package PLAN_FILE BASE HEAD`를 절대 경로로, 내가 실행 중인 작업 트리에서 실행 — 작성한 고유 파일 경로를 출력한다. BASE는 구현자 파견 전에 기록한 커밋이다. `HEAD~1`은 다중 커밋 태스크의 마지막 커밋만 남기고 조용히 버리므로 절대 쓰지 않는다), 그 경로로 태스크 리뷰어를 파견한다.

**그 밖의 모든 상태**(DONE_WITH_CONCERNS, NEEDS_CONTEXT, BLOCKED): [`references/handling-reports.md`](../../../skills/subagent-driven-development/references/handling-reports.md)를 읽고 따른다. 그런 상태를 받을 때마다 매번.

구현자가 질문하면 — 시작 전이든 작업 중이든 — 명확하고 완전하게 답하고, 필요하면 컨텍스트를 더 주고, 구현으로 서둘러 밀어넣지 않는다.

### 3. 태스크를 리뷰한다

태스크별 리뷰는 **태스크 범위의 게이트**다. 폭넓은 리뷰는 최종 브랜치 전체 리뷰에서 한 번 일어난다. 태스크 리뷰를 절대 건너뛰지 않고, 두 평결 중 하나라도 빠진 리포트를 받아들이지 않는다 — **스펙 준수와 태스크 품질 둘 다 필수다.** 구현자의 셀프 리뷰가 태스크 리뷰를 대체하지 않는다. 둘 다 필요하다.

- 리뷰어에게 diff를 **파일로** 준다: 이 스킬의 `bash scripts/review-package PLAN_FILE BASE HEAD`를 절대 경로로, 내가 실행 중인 작업 트리에서 실행하고 출력된 파일 경로를 리뷰어에게 넘긴다(bash가 없으면 `git log --oneline`, `git diff --stat`, 그 범위의 `git diff -U10`을 고유한 파일 하나로 리다이렉트). 그러면 그 출력이 내 컨텍스트에 들어오지 않고, 리뷰어는 커밋 목록, stat 요약, 컨텍스트가 붙은 전체 diff를 Read 호출 한 번으로 본다. 구현자 파견 전에 기록한 BASE를 쓴다 — `HEAD~1`은 다중 커밋 태스크를 조용히 잘라낸다. **diff 파일 없이 태스크 리뷰어를 파견하지 않는다**
- **리뷰어 입력:** 태스크 리뷰어는 경로 세 개를 받는다 — 같은 브리프 파일, 리포트 파일, 리뷰 패키지 — 그리고 그 태스크를 구속하는 전역 제약
- 리뷰어에게 주는 전역 제약 블록은 그의 **주의 렌즈**다. 계획의 Global Constraints 섹션이나 스펙에서 구속력 있는 요구사항을 그대로 복사한다: 정확한 값, 정확한 형식, 컴포넌트 간 명시된 관계("X와 같은 레이아웃", "Y와 일치"). 리뷰어 템플릿은 이미 프로세스 규칙(YAGNI, 테스트 위생, 리뷰 방법)을 담고 있다 — 제약 블록은 **이 프로젝트의 스펙이 요구하는 것**을 위한 자리다
- 구체적이고 태스크 특정적인 이유 없이 "모든 사용처를 확인하라", "유용하면 race 테스트를 돌려라" 같은 열린 지시를 추가하지 않는다
- 구현자가 같은 코드에 대해 이미 돌린 테스트를 리뷰어에게 다시 돌리라고 하지 않는다 — 구현자의 리포트가 테스트 증거를 담고 있다
- **리뷰어를 위해 발견을 미리 판단하지 않는다** — 특정 이슈를 무시하거나 지적하지 말라고 지시하는 일은 절대 없다. 어떤 발견이 오탐일 것 같으면, 리뷰어가 제기하게 두고 리뷰 루프에서 판정한다. 내가 쓰고 있는 프롬프트에 "지적하지 마라", "X를 결함으로 취급하지 마라", "최대 Minor", "계획이 그렇게 정했다"가 들어 있다면 멈춰라 — 미리 판단하고 있는 것이고, 보통은 리뷰 루프를 아끼려는 것이다

리뷰어가 "⚠️ Cannot verify from diff"(diff로는 검증 불가) 항목을 보고하면, 태스크를 완료로 표시하기 전에 [`references/cannot-verify.md`](../../../skills/subagent-driven-development/references/cannot-verify.md)를 읽는다.

템플릿: [task-reviewer-prompt.md](../../../skills/subagent-driven-development/task-reviewer-prompt.md)

### 4. 수정 루프

리뷰가 스펙 ❌, Critical이나 Important 발견, 또는 내가 실제 결함으로 확인한 ⚠️ 항목을 보고하면 루프가 작동한다.

루프가 작동하면 [`references/fix-loop.md`](../../../skills/subagent-driven-development/references/fix-loop.md)를 읽고 따른다. 이 세션에서 앞서 읽었더라도 **매 라운드 전에 다시 읽는다**: 거기에 라운드 상한, 브레이커, 각 라운드가 원장에 쓰는 줄이 들어 있고, 그 내용에 대한 내 기억은 컴팩션을 견디지 못한다.

### 5. 태스크를 완료한다

리뷰가 깨끗하게 돌아오거나 — 또는 상한에서 모든 미해결 발견이 판정과 함께 park되면 — 다른 사무 작업과 같은 메시지에 완료 줄을 원장에 추가한다:

- `Task <N>: complete (commits <base7>..<head7>, review clean)`
- 브레이커가 작동한 경우: `Task <N>: complete (commits <base7>..<head7>, <K> parked)`

그다음 todo를 완료로 표시하고 넘어간다. 리뷰에 미해결 Critical/Important가 있고 그것이 수정되지도, 상한에서 판정과 함께 park되지도 않았다면 다음 태스크로 넘어가지 않는다.

## 최종 리뷰

모든 태스크가 완료되면 [`references/final-review.md`](../../../skills/subagent-driven-development/references/final-review.md)를 읽고 따른다. 브랜치 전체 리뷰, 그에 대한 단 한 번의 수정 물결, 그리고 마무리하는 방법을 다룬다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "스펙 준수는 이 정도면 됐어" | 리뷰어가 스펙 결함을 찾았다 = 안 끝났다. 고치거나 상한에 도달해 판정하거나, 출구는 그 둘뿐이다. |
| "내가 고치는 게 낫지, 파견은 오버헤드야" | 컨트롤러의 수정은 내 컨텍스트를 오염시키고 리뷰를 건너뛴다. 구현자를 재개하라. |
| "한 라운드만 더 하면 수렴할 거야" | 상한을 넘으면 라운드는 수렴하지 않는다 — 실패가 구조적이다. 판정하고 경로를 정하라. |
| "어차피 리뷰어가 새 걸 찾아낼 텐데" | 범위 한정 재리뷰는 수정을 검증할 뿐 떠돌 수 없다. 손대지 않은 코드의 새 발견은 루프가 아니라 원장으로 간다. |
| "이 발견은 명백히 틀렸으니 버리자" | 판정은 상한에서만 하고, 모든 판정은 원장 항목이다. 조용한 폐기는 금지다. |
| "수정이 작았으니 재리뷰는 건너뛰자" | 리뷰 안 된 수정이 회귀를 불러들인다. 모든 라운드는 범위 한정 재리뷰로 끝난다. |
| "리뷰가 루프를 느리게 해" | 리뷰 없는 루프는 검증되지 않은 소용돌이일 뿐이다. 리뷰가 루프의 브레이크이자 핸들이다. |
| "원장 기록은 오버헤드야" | 원장이 컴팩션을 견디는 것이다. 원장 없는 컨트롤러는 완료된 태스크 시퀀스 전체를 재파견해 왔다. |
| "구현자가 자기 리뷰어를 띄웠네 — 공짜 추가 보증" | 같은 diff를 보는 중복 좌석이고, 게이트는 태스크 리뷰다. 작업자가 스폰한 리뷰어는 엄밀함이 아니라 **지적해야 할 결함**이다. |
