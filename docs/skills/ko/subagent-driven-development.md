# subagent-driven-development — 서브에이전트 주도 개발 (SDD)

> 원문: [`skills/subagent-driven-development/SKILL.md`](../../../skills/subagent-driven-development/SKILL.md)
> 트리거(원문 유지): `Use when executing implementation plans with independent tasks in the current session`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

태스크마다 새 구현자 서브에이전트를 파견하고, 각 태스크 후에 태스크 리뷰(스펙 준수 + 코드 품질)를 하고, 마지막에 브랜치 전체에 대한 폭넓은 리뷰를 해서 계획을 실행한다.

**왜 서브에이전트인가:** 격리된 컨텍스트를 가진 전문 에이전트에게 태스크를 위임한다. 지시와 컨텍스트를 정밀하게 구성함으로써 그들이 집중을 유지하고 태스크에 성공하게 만든다. 그들은 **내 세션의 컨텍스트나 히스토리를 절대 상속받지 않는다** — 그들에게 필요한 것을 내가 정확히 구성해 준다. 이것은 내 컨텍스트도 조정 작업용으로 보존해 준다.

**핵심 원칙:** 태스크마다 새 서브에이전트 + 태스크 리뷰(스펙 + 품질) + 폭넓은 최종 리뷰 = 높은 품질, 빠른 반복

**서술:** 툴 호출 사이에는 짧은 한 줄까지만 — 원장과 툴 결과가 기록을 담당한다.

**연속 실행:** 태스크 사이에 사람 파트너에게 확인하려고 멈추지 않는다. 계획의 모든 태스크를 멈추지 않고 실행한다. 멈출 이유는 아래 네 가지 또는 전체 완료뿐이다. "계속할까요?" 프롬프트와 진행 요약은 그들의 시간을 낭비한다 — 계획을 실행해 달라고 했으니 실행하라.

**판정(Ruling)이지 정지가 아니다.** 실행 중인 계획은 사람을 기다리지 않는다. 충돌, 모호함, 계획 결함, 초과하겠다고 물었을 법한 상한 — 직접 결정한다. **스펙이 구속력 있는 권위이고, 계획은 그 논증이며, 둘 다 답하지 않는 것은 내 판단이 결정한다.** 모든 결정을 원장에 `Ruling: <무엇을 결정했는지> — <왜> — <틀렸을 때의 비용>`로 기록하고 계속 간다. 잘못된 판정은 파트너가 보고 되돌릴 수 있는 재작업 비용이지만, 질문 앞에 멈춰 선 세션은 그들의 하루 전체를 쓰고 아무것도 사지 못한다.

멈추는 것은 딱 네 가지다: 되돌릴 수 없거나 파괴적인 작업, 보안에 민감한 작업, 이 워크트리 밖으로 나가는 부수효과 중 통상 먼저 물어야 하는 것(머지, 공유 브랜치 푸시, 배포), 그리고 어떤 길도 추측일 만큼 망가진 계획.

## 언제 쓰나

```
구현 계획이 있는가?
 ├─ 아니오 → 수동 실행 또는 브레인스토밍 먼저
 └─ 예 → 태스크가 대체로 독립적인가?
      ├─ 아니오(강하게 결합) → 수동 실행 또는 브레인스토밍 먼저
      └─ 예 → 파트너가 인라인을 골랐거나 서브에이전트 도구가 없는가?
           ├─ 예 → executing-plans
           └─ 아니오 → subagent-driven-development
```

**executing-plans(인라인)와의 비교:**
- 하나의 컨텍스트가 모든 태스크를 하는 대신, 태스크마다 새 서브에이전트(컨텍스트 오염 없음)
- 마지막에만 리뷰하는 대신, 태스크마다 리뷰(스펙 준수 + 코드 품질)
- 태스크마다, 리뷰마다 새 컨텍스트 비용이 든다. 인라인은 컨텍스트 하나 + 최종 리뷰어 하나
- 둘 다 이 세션에서 돌고, 같은 계획 워크스페이스와 원장을 공유하며, 태스크 사이에 멈추지 않는다

## 셋업

작업이 격리된 공간에서 일어나게 한다: superpowers:using-git-worktrees로 만들거나 기존 것을 확인한다. 사람 파트너의 명시적 동의 없이 main/master에서 구현을 시작하지 않는다.

대화 기억은 컴팩션을 견디지 못한다. 실제 세션에서 자기 위치를 잃은 컨트롤러가 **이미 완료된 태스크 전체를 재파견**한 사례가 있다 — 관찰된 것 중 가장 비싼 실패다. 진행 상황을 todo가 아니라 원장 파일에 추적한다.

- 각 계획은 워크스페이스를 소유한다. 스킬 시작 시 이 스킬의 `bash scripts/sdd-workspace PLAN_FILE`을 실행하면 계획의 git-ignore된 디렉터리(`<repo-root>/.superpowers/sdd/` 아래)를 출력한다. **이 계획의** 모든 산출물(원장, 브리프, 리포트, 리뷰 패키지)이 여기 산다. 다른 계획의 디렉터리는 절대 읽거나 쓰지 않는다
- `<workspace>/progress.md`에 이 계획의 원장이 있는지 확인한다. 첫 줄이 내 계획 파일을 가리키면 `Task <N>: complete` 줄이 있는 태스크는 끝난 것이다 — 재파견하지 않고 그 줄이 없는 첫 태스크에서 재개한다. 마지막 줄이 수정 라운드인 태스크는 루프 중간이다. 다음 라운드에서 루프를 재개한다. 첫 줄이 다른 계획 파일을 가리키는 원장 — 또는 옛 평면 경로 `.superpowers/sdd/progress.md`에 있는 떠돌이 원장 — 은 다른 계획의 진행 기록이다. 그대로 두고 내 것을 새로 시작한다
- 원장을 만들 때 첫 줄에 정체를 적는다: `# SDD ledger — plan: <계획 파일 경로>`
- **원장은 내 복구 지도다.** 거기 적힌 커밋은 내 컨텍스트가 그것을 만든 기억을 잃어도 git에 존재한다. 컴팩션 이후에는 내 기억보다 원장과 `git log`를 믿는다
- `git clean -fdx`는 워크스페이스를 파괴한다(git-ignore된 스크래치다). 그러면 `git log`에서 복구한다

계획을 한 번 읽고, 맥락과 Global Constraints를 기록하고, 태스크마다 todo를 만든다. 계획이 Spec을 지정하면 그것도 읽는다: 스펙은 계획이 논증하는 권위이고, 계획 내부의 충돌은 스펙에 비추어 해소된다. 닿을 수 있는 스펙이 없는 계획은 그 사실을 원장 노트로 남긴다 — 그 없이 내린 판정은 잠정적이다.

Task 1을 파견하기 전에 계획을 한 번 스캔해 충돌을 찾되, 확인하는 대로 확인한 내용을 적는다:

- 서로 또는 계획의 Global Constraints와 모순되는 태스크
- 계획이 명시적으로 요구하는데 리뷰 루브릭이 결함으로 취급하는 것(아무것도 단언하지 않는 테스트, 로직 블록의 글자 그대로 복제)

**스캔의 산출물은 평결이 아니라 표다.** 파일이나 인터페이스를 공유하는 모든 태스크 쌍마다 한 줄: 두 태스크, 한쪽이 생산하는 것과 다른 쪽이 소비하는 것, 발견한 것. 모든 태스크마다 한 줄: 그 텍스트가 자기 자신과 일치하는가 — 지정한 테스트 대 지정한 코드, 생성하는 파일 대 나중에 건드리는 파일. 그 줄들 없이 "스캔은 깨끗하다"고 하는 것은 돌린 스캔이 아니다.

표를 원장에 쓴다. 실행을 시작하기 전에 발견한 모든 것을 판정하고 — 각 발견을 그것을 요구하는 계획 텍스트에 대조해서 — 각 판정을 원장에 기록한다. 스캔이 깨끗하면 언급 없이 진행한다. 스펙을 구속력 있는 권위로 삼아 판정하고, 판정을 그 줄 옆에 기록하고, Task 1을 파견한다. 리뷰 루프는 구현에서만 드러나는 충돌을 잡는 그물로 남는다.

## 모델 선택

비용을 아끼고 속도를 높이기 위해 각 역할을 감당할 수 있는 **가장 약한 모델**을 쓴다.

**기계적 구현 태스크**(독립 함수, 명확한 스펙, 1~2개 파일): 빠르고 싼 모델. 계획이 잘 명세되어 있으면 대부분의 구현 태스크는 기계적이다.

**통합과 판단 태스크**(다중 파일 조율, 패턴 매칭, 디버깅): 표준 모델.

**아키텍처와 설계 태스크**: 가장 유능한 모델. **최종 브랜치 전체 리뷰가 여기 해당한다** — 세션 기본값이 아니라 가장 유능한 모델로 파견한다.

**리뷰 태스크**: 같은 판단을 diff의 크기·복잡도·위험에 맞춰 적용한다. 작은 기계적 diff에는 가장 유능한 모델이 필요 없고, 미묘한 동시성 변경에는 필요하다. 작은 수정 diff의 범위 한정 재리뷰는 싸거나 중간 티어로.

**수정 루프 에스컬레이션(4~5라운드)**: 막힌 구현자보다 **최소 한 티어 위** 모델.

**서브에이전트를 파견할 때는 항상 모델을 명시적으로 지정한다.** 생략하면 내 세션 모델 — 보통 가장 유능하고 가장 비싼 — 을 상속하며, 이 절이 조용히 무력화된다.

**턴 수가 토큰 단가를 이긴다.** 실제 시간과 컨텍스트 비용은 서브에이전트가 몇 턴을 쓰느냐에 비례하며, 가장 싼 모델은 다단계 작업에서 일상적으로 2~3배의 턴을 쓴다 — 결국 더 비싸다. 리뷰어와 산문 설명으로 작업하는 구현자에게는 **중간 티어를 하한으로** 쓴다. 태스크의 계획 텍스트에 쓸 코드가 전부 들어 있다면 구현은 전사 + 테스트다. 그런 구현자에게는 가장 싼 티어를 쓴다. 단일 파일 기계적 수정도 가장 싼 티어.

**태스크 복잡도 신호(구현 태스크):**
- 완전한 스펙으로 1~2개 파일을 건드림 → 싼 모델
- 통합 고려사항이 있는 여러 파일 → 표준 모델
- 설계 판단이나 코드베이스 전반 이해 필요 → 가장 유능한 모델

## 태스크 루프

**같은 모양의 작은 작업은 묶는다.** 계획이 각각 같은 종류의 작고 독립적인 편집인 태스크를 여러 개 나열한다면 — 여러 파일에 반복되는 같은 한 줄 수정, 상수 변경, 필드 추가 — 태스크마다 서브에이전트를 파견하지 **않는다**. 모든 파일과 그 변경을 나열한 파견 브리프 **하나**를 구성해 전체 묶음을 서브에이전트 하나에게 보내고, 그 diff를 하나의 단위로 리뷰한다. 태스크당 하나의 파견은 자기만의 판단, 자기만의 테스트, 자기만의 리뷰 표면이 필요한 작업에만 쓴다.

파견 프롬프트에 붙여넣는 모든 것과 서브에이전트가 되돌려 출력하는 모든 것은 세션이 끝날 때까지 내 컨텍스트에 남고 이후 모든 턴에서 다시 읽힌다. **산출물은 파일로 주고받는다.**

**파견된 서브에이전트 대기:** 짧은 타임아웃으로 대기 인터페이스를 폴링하지 않고, 조용한 무한 대기에 앉아 있지도 않는다. 로컬 작업(원장 갱신, 다음 리뷰 패키징, 리포트 읽기)이 있는 동안에는 계속 일한다. 자식의 결과는 알아서 도착한다. 정말로 할 일이 없을 때는 **경계가 있는 구간**(플랫폼이 허용하면 5~10분)으로 기다리고, 구간 사이에 상태 한 줄을 남기고 살아 있는 자식들을 대조한다: 목록을 뽑고, 보고 없이 끝난 것을 추적한다. 경계 있는 구간은 긴 대기의 효율을 거의 다 유지하면서, 막히거나 유실된 자식을 세션 끝이 아니라 몇 분 안에 알아채게 해준다.

### 1. 구현자를 파견한다

파견 전에 BASE(`git rev-parse HEAD`)를 기록한다 — 리뷰 패키지와 수정 라운드 diff에 필요하다.

- **태스크 브리프:** 구현자를 파견하기 전에 이 스킬의 `bash scripts/task-brief PLAN_FILE N`을 실행한다. 태스크의 전체 텍스트를 고유한 이름의 파일로 추출하고 경로를 출력한다. **브리프가 요구사항의 단일 출처로 남도록** 파견을 구성한다. 파견에는 다음이 들어간다: (1) 이 태스크가 프로젝트에서 어디에 들어가는지 한 줄, (2) 브리프 경로 — "먼저 이것을 읽어라. 이것이 네 요구사항이며, 정확한 값을 그대로 쓴다"고 소개, (3) 브리프가 알 수 없는, 앞선 태스크의 인터페이스와 결정, (4) 브리프에서 내가 발견한 모호함에 대한 내 해소, (5) 리포트 파일 경로와 리포트 계약. **정확한 값(숫자, 매직 스트링, 시그니처, 테스트 케이스)은 브리프에만 나타난다.** 서브에이전트에게 계획 파일 전체를 읽게 하지 않는다
- **리포트 파일:** 구현자의 리포트 파일 이름을 브리프에 맞춰 짓고(브리프 `…/task-N-brief.md` → 리포트 `…/task-N-report.md`) 파견 프롬프트에 넣는다. 구현자는 전체 리포트를 거기 쓰고, 돌려주는 것은 상태, 커밋, 한 줄 테스트 요약, 우려뿐이다
- 파견 프롬프트는 **태스크 하나를 서술하지 세션 히스토리를 서술하지 않는다.** 누적된 이전 태스크 요약("Tasks 1-3 이후 상태")을 이후 파견에 붙여넣지 않는다 — 실제 세션의 파견이 42,000자에 달했는데 그중 99%가 붙여넣은 히스토리였다. 새 서브에이전트에게 필요한 것은 자기 태스크, 자기가 건드리는 인터페이스, 전역 제약뿐이다
- 파견은 **서브에이전트 금지 계약**을 담는다(구현자 템플릿에 들어 있다): 구현자는 서브에이전트를 파견하지 않는다 — 헬퍼도, 리뷰어는 더더욱. 리뷰는 리포트 이후 나로부터 온다. 실제 세션에서 작업자가 스폰한 리뷰어는 전부 컨트롤러가 어차피 파견한 태스크 리뷰를 중복했다 — 태스크당 리뷰 좌석 하나가 통째로 더 든 셈이다
- 앞선 태스크가 이 태스크가 건드리는 영역에 발견을 park해 뒀다면, 그 원장 항목에 대한 포인터를 파견에 담는다
- 파견 결과에서 구현자의 에이전트 식별자를 기록한다 — 수정 루프 1~3라운드가 이 에이전트를 재개한다
- **구현 서브에이전트를 병렬로 여러 개 파견하지 않는다**(충돌)

템플릿: [implementer-prompt.md](../../../skills/subagent-driven-development/implementer-prompt.md)

### 2. 리포트를 처리한다

구현자 서브에이전트는 네 가지 상태 중 하나를 보고한다. 각각 적절히 처리한다:

**DONE:** 리뷰 패키지를 생성하고(`bash scripts/review-package PLAN_FILE BASE HEAD`, 이 스킬 디렉터리에서 실행 — 작성한 고유 파일 경로를 출력한다. BASE는 구현자 파견 전에 기록한 커밋이다. `HEAD~1`은 다중 커밋 태스크의 마지막 커밋만 남기고 조용히 버리므로 절대 쓰지 않는다), 그 경로로 태스크 리뷰어를 파견한다.

**DONE_WITH_CONCERNS:** 구현자가 작업은 마쳤지만 의문을 표시했다. 진행 전에 그 우려를 읽는다. 정확성이나 범위에 관한 우려라면 리뷰 전에 해결한다. 관찰("이 파일이 커지고 있다" 등)이라면 기록하고 리뷰로 진행한다.

**NEEDS_CONTEXT:** 제공되지 않은 정보가 필요하다. 빠진 컨텍스트를 제공하고 재파견한다.

**BLOCKED:** 구현자가 태스크를 완료할 수 없다. 막힌 지점을 평가한다:
1. 컨텍스트 문제라면 컨텍스트를 더 주고 **같은 모델로** 재파견
2. 더 많은 추론이 필요하면 **더 유능한 모델로** 재파견
3. 태스크가 너무 크면 더 작게 쪼갠다
4. 계획 자체가 틀렸다면 수정을 판정하고, 원장에 남기고, 그 판정을 파견에 실어 재파견

**절대** 에스컬레이션을 무시하거나 변경 없이 같은 모델에게 재시도를 강요하지 않는다. 구현자가 막혔다고 했다면 무언가 바뀌어야 한다.

구현자가 질문하면 — 시작 전이든 작업 중이든 — 명확하고 완전하게 답하고, 필요하면 컨텍스트를 더 주고, 구현으로 서둘러 밀어넣지 않는다.

### 3. 태스크를 리뷰한다

태스크별 리뷰는 **태스크 범위의 게이트**다. 폭넓은 리뷰는 최종 브랜치 전체 리뷰에서 한 번 일어난다. 태스크 리뷰를 절대 건너뛰지 않고, 두 평결 중 하나라도 빠진 리포트를 받아들이지 않는다 — **스펙 준수와 태스크 품질 둘 다 필수다.** 구현자의 셀프 리뷰가 태스크 리뷰를 대체하지 않는다. 둘 다 필요하다.

- 리뷰어에게 diff를 **파일로** 준다: 이 스킬의 `bash scripts/review-package PLAN_FILE BASE HEAD`를 실행하고 출력된 파일 경로를 리뷰어에게 넘긴다(bash가 없으면 `git log --oneline`, `git diff --stat`, 그 범위의 `git diff -U10`을 고유한 파일 하나로 리다이렉트). 그러면 그 출력이 내 컨텍스트에 들어오지 않고, 리뷰어는 커밋 목록, stat 요약, 컨텍스트가 붙은 전체 diff를 Read 호출 한 번으로 본다. 구현자 파견 전에 기록한 BASE를 쓴다 — `HEAD~1`은 다중 커밋 태스크를 조용히 잘라낸다. **diff 파일 없이 태스크 리뷰어를 파견하지 않는다**
- **리뷰어 입력:** 태스크 리뷰어는 경로 세 개를 받는다 — 같은 브리프 파일, 리포트 파일, 리뷰 패키지 — 그리고 그 태스크를 구속하는 전역 제약
- 리뷰어에게 주는 전역 제약 블록은 그의 **주의 렌즈**다. 계획의 Global Constraints 섹션이나 스펙에서 구속력 있는 요구사항을 그대로 복사한다: 정확한 값, 정확한 형식, 컴포넌트 간 명시된 관계("X와 같은 레이아웃", "Y와 일치"). 리뷰어 템플릿은 이미 프로세스 규칙(YAGNI, 테스트 위생, 리뷰 방법)을 담고 있다 — 제약 블록은 **이 프로젝트의 스펙이 요구하는 것**을 위한 자리다
- 구체적이고 태스크 특정적인 이유 없이 "모든 사용처를 확인하라", "유용하면 race 테스트를 돌려라" 같은 열린 지시를 추가하지 않는다
- 구현자가 같은 코드에 대해 이미 돌린 테스트를 리뷰어에게 다시 돌리라고 하지 않는다 — 구현자의 리포트가 테스트 증거를 담고 있다
- **리뷰어를 위해 발견을 미리 판단하지 않는다** — 특정 이슈를 무시하거나 지적하지 말라고 지시하는 일은 절대 없다. 어떤 발견이 오탐일 것 같으면, 리뷰어가 제기하게 두고 리뷰 루프에서 판정한다. 내가 쓰고 있는 프롬프트에 "지적하지 마라", "X를 결함으로 취급하지 마라", "최대 Minor", "계획이 그렇게 정했다"가 들어 있다면 멈춰라 — 미리 판단하고 있는 것이고, 보통은 리뷰 루프를 아끼려는 것이다

태스크 리뷰어는 "⚠️ Cannot verify from diff"(diff로는 검증 불가) 항목을 보고할 수 있다 — 변경되지 않은 코드에 있거나 태스크를 가로지르는 요구사항이다. 이것이 나머지 리뷰를 막지는 않지만, 태스크를 완료로 표시하기 전에 **각각을 내가 직접 해소해야 한다**. 리뷰어에게 없는 계획과 태스크 간 맥락을 내가 갖고 있다. 실제 결함이라고 확인되면 스펙 리뷰 실패로 취급한다 — 다른 발견들과 함께 수정 루프에 들어간다.

템플릿: [task-reviewer-prompt.md](../../../skills/subagent-driven-development/task-reviewer-prompt.md)

### 4. 수정 루프

리뷰가 스펙 ❌, Critical이나 Important 발견, 또는 내가 실제 결함으로 확인한 ⚠️ 항목을 보고하면 루프가 작동한다.

루프가 시작되기 전에, 두 경로가 즉시 빠져나간다:

- **Minor 발견**은 진행하면서 원장에 기록한다(`Task <N>: minor (deferred): <한 줄>`). 그리고 최종 브랜치 전체 리뷰가 그 목록을 보고 머지 전에 무엇을 꼭 고쳐야 하는지 분류할 수 있게 가리킨다. 아무도 읽지 않는 롤업은 조용한 폐기다. Minor는 절대 루프에 들어가지 않는다
- **plan-mandated로 표시된 발견** — 또는 계획 텍스트가 요구하는 것과 충돌하는 모든 발견 — 은 내가 판정할 몫이다: 발견을 계획 텍스트에 견주어 저울질하고, 스펙을 구속력 있는 권위로 삼아 결정하고, 행동하기 전에 판정을 원장에 남긴다. 계획이 요구한다는 이유로 발견을 기각하지 않고, 기록된 판정 없이 계획에 반하는 수정을 파견하지 않는다

나머지는 전부 루프에 들어간다. **수정 라운드 하나 = 수정 파견 하나 + 범위 한정 재리뷰 하나.** 태스크당 최대 5라운드:

**1~3라운드 — 원래 구현자를 재개한다.** 미해결 발견을 그대로 보낸다. 그의 컨텍스트는 온전하다. 태스크도, 코드도, 자기 선택도 안다. 하네스가 살아 있는 서브에이전트에게 메시지를 더 보낼 수 없다면, 브리프 경로·리포트 파일 경로·발견을 담아 새 구현자를 파견한다 — 어느 쪽이든 리포트 파일이 지속되는 기억이다.

**4~5라운드 — 더 유능한 모델로 새 구현자를 파견한다**(모델 선택 참고). 브리프 경로, 리포트 파일 경로, 미해결 발견, 그리고 이 구도와 함께: "이전 구현자가 이 태스크를 [N]번 시도했다. 이제 네가 소유한다. 무엇을 시도했는지는 리포트 파일을 읽어라." 재개를 세 번 견딘 루프는 보통 구현자가 자기 문제를 보지 못한다는 뜻이다 — 새로운 눈과 능력 상향을 한 번에.

**매 라운드, 어느 쪽이든:** 구현자가 고치고, 수정된 코드를 커버하는 테스트를 다시 돌리고, 같은 리포트 파일에 수정 리포트를 덧붙이고, 짧은 계약을 반환한다. 리뷰어를 재파견하기 전에, 수정 리포트에 커버하는 테스트, 실행한 명령, 그 출력이 들어 있는지 확인한다. 셋이 다 있을 때 재리뷰를 파견한다. 수정 메시지에 커버하는 테스트 파일 이름을 적는다 — 한 줄 수정에 전체 스위트는 필요 없다.

**재리뷰는 범위가 한정된다.** `bash scripts/review-package PLAN_FILE FIX_BASE HEAD`를 실행하고(FIX_BASE는 이전 리뷰가 본 head) [re-review-prompt.md](../../../skills/subagent-driven-development/re-review-prompt.md)를 발견 목록, 브리프, 리포트 파일, 출력된 diff 경로와 함께 파견한다. 재리뷰어는 각 발견을 ADDRESSED 또는 NOT ADDRESSED로 평결하고 **수정 diff 안에서만** 새 파손을 표시한다. 수정 diff의 새 Critical/Important 파손은 미해결 목록에 합류한다. 범위 밖 관찰은 지연된 minor로 원장에 간다 — 절대 루프를 연장하지 않는다.

**매 라운드 후** 원장에 추가한다:
`Task <N>: fix round <R>/5 (<X> addressed, <Y> open — <발견 한 줄들>; commits <a7>..<b7>)`

**컨트롤러 세션에서 발견을 직접 고치지 않는다** — 내 컨텍스트는 조정용으로 깨끗하게 유지되고, 컨트롤러의 수정은 리뷰를 건너뛴다.

**브레이커.** 5라운드의 재리뷰에도 발견이 남으면 파견을 멈춘다. 미해결 발견을 **내가 직접 판정한다** — 리뷰어에게 없는 계획과 태스크 간 맥락을 내가 갖고 있다:

- **리뷰어가 틀렸거나 논쟁의 여지가 있다:** park한다 — `Task <N>: parked — <발견> — Ruling: <왜 코드가 그대로인지>`. 최종 리뷰가 양쪽을 다 본다
- **실재하지만 아무것도 그 위에 서 있지 않다:** 같은 방식으로 park하되, 실재하며 미룬다는 판정을 함께 적는다
- **실재하고 구조를 떠받친다** — 이후 태스크가 그 위에 서거나, 계획 결함을 드러낸다: 의존하는 작업을 풀어줄 **가장 작은 변경**을 판정하고, `Task <N>: Ruling: <발견> — <무엇을 왜 결정했는지>`로 원장에 남기고, 다음 태스크의 파견에 실어 나른다. 구조적 실패를 조용히 park하면 의존하는 모든 태스크가 그 위에 쌓인다. 그 결함 때문에 모든 길이 추측이 될 때만 멈춘다

**상한에서만 판정한다.** 루프를 끝내려고 더 일찍 판정하는 것은 이름만 다른 사전 판단이다. 모든 판정은 원장 항목이다 — **조용한 폐기는 금지된다.**

### 5. 태스크를 완료한다

리뷰가 깨끗하게 돌아오거나 — 또는 상한에서 모든 미해결 발견이 판정과 함께 park되면 — 다른 사무 작업과 같은 메시지에 완료 줄을 원장에 추가한다:

- `Task <N>: complete (commits <base7>..<head7>, review clean)`
- 브레이커가 작동한 경우: `Task <N>: complete (commits <base7>..<head7>, <K> parked)`

그다음 todo를 완료로 표시하고 넘어간다. 리뷰에 미해결 Critical/Important가 있고 그것이 수정되지도, 상한에서 판정과 함께 park되지도 않았다면 다음 태스크로 넘어가지 않는다.

## 최종 리뷰

최종 브랜치 전체 리뷰도 패키지를 받는다: `bash scripts/review-package PLAN_FILE MERGE_BASE HEAD`를 실행하고(MERGE_BASE = 브랜치가 시작된 커밋, 예: `git merge-base main HEAD`) 출력된 경로를 최종 리뷰 파견에 넣어, 최종 리뷰어가 git 명령으로 브랜치 diff를 다시 유도하는 대신 파일 하나를 읽게 한다. **가장 유능한 모델로 파견하고**(모델 선택 참고), superpowers:requesting-code-review의 [code-reviewer.md](../../../skills/requesting-code-review/code-reviewer.md)를 쓴다. 원장의 지연 minor와 park된 줄을 가리켜서 머지 전에 무엇을 고쳐야 하는지 분류하게 한다.

최종 브랜치 전체 리뷰가 발견을 반환하면, **완전한 발견 목록을 담아 수정 서브에이전트 하나를 파견한다** — 발견마다 수정자를 하나씩 두지 않는다. 발견별 수정자는 각자 컨텍스트를 다시 쌓고 스위트를 다시 돌린다. 실제 세션에서 최종 리뷰 수정 물결이 모든 태스크를 합친 것보다 비쌌다. 그다음 수정 물결에 대한 범위 한정 재리뷰를 **정확히 한 번** 돌린다(수정 범위에 대해 `bash scripts/review-package PLAN_FILE FIX_BASE HEAD`, [re-review-prompt.md](../../../skills/subagent-driven-development/re-review-prompt.md)). 잔여 발견은 태스크 루프의 브레이커처럼 판정한다: 판정과 함께 park하거나, 구조를 떠받치는 것은 판정하고 결정을 원장에 남긴다. 여기서도 위 네 부류만이 멈추게 한다. **두 번째 수정 물결은 없다** — 구조를 떠받치는 잔여 발견은 finishing-a-development-branch가 선택지를 제시할 때 사람 파트너에게 올라간다.

## 마무리

무엇이든 삭제하기 전에, `Ruling:`이 들어간 모든 원장 줄을 — 사전 스캔 판정, park된 발견, 브레이커 판정, 전부 — 만든 순서대로 최종 메시지의 "Rulings I made" 아래에 모으고 각각 틀렸을 때의 비용을 적는다. **목록은 빠짐없다:** 원장에 판정이 있으면 목록에도 있다. 그 목록이 내가 사람 파트너를 대신해 내린 결정이 그들에게 도달하는 **유일한 장소**다 — 그들이 읽고 내가 틀린 것을 다시 작업한다. 워크스페이스와 함께 사라진 판정은 **비밀리에 내린 결정**이었다.

최종 브랜치 전체 리뷰가 깨끗하고 그 수정이 머지되면, 이 계획의 워크스페이스를 삭제한다(`rm -rf <workspace>`) — 이제 git 히스토리가 기록이다. 형제 디렉터리는 다른 계획의 것이니 건드리지 않는다.

superpowers:finishing-a-development-branch를 사용한다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "스펙 준수는 이 정도면 됐어" | 리뷰어가 스펙 결함을 찾았다 = 안 끝났다. 고치거나 상한에 도달해 판정하거나, 출구는 그 둘뿐이다. |
| "내가 고치는 게 낫지, 파견은 오버헤드야" | 컨트롤러의 수정은 내 컨텍스트를 오염시키고 리뷰를 건너뛴다. 구현자를 재개하라. |
| "한 라운드만 더 하면 수렴할 거야" | 상한을 넘으면 라운드는 수렴하지 않는다 — 실패가 구조적이다. 판정하고 경로를 정하라. |
| "어차피 리뷰어가 새 걸 찾아낼 텐데" | 범위 한정 재리뷰는 수정을 검증할 뿐 떠돌 수 없다. 손대지 않은 코드의 새 발견은 루프가 아니라 원장으로 간다. |
| "이 발견은 명백히 틀렸으니 버리자" | 판정은 상한에서만 하고, 모든 판정은 원장 항목이다. 조용한 폐기는 금지다. |
| "수정이 작았으니 재리뷰는 건너뛰자" | 리뷰 안 된 수정이 회귀를 불러들인다. 모든 라운드는 범위 한정 재리뷰로 끝난다. |
| "리뷰가 루프를 느리게 해" | 리뷰 없는 루프는 검증되지 않은 소용돌이일 뿐이다. 리뷰가 루프의 브레이크이자 핸들이다. |
| "원장 기록은 오버헤드야" | 원장이 컴팩션을 견디는 것이다. 원장 없는 컨트롤러는 완료된 태스크 시퀀스 전체를 재파견해 왔다. |
| "구현자가 자기 리뷰어를 띄웠네 — 공짜 추가 보증" | 같은 diff를 보는 중복 좌석이고, 게이트는 태스크 리뷰다. 작업자가 스폰한 리뷰어는 엄밀함이 아니라 **지적해야 할 결함**이다. |
