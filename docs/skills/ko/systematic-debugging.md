# systematic-debugging — 체계적 디버깅

> 원문: [`skills/systematic-debugging/SKILL.md`](../../../skills/systematic-debugging/SKILL.md)
> 트리거(원문 유지): `Use when encountering any bug, test failure, or unexpected behavior, before proposing fixes`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

**핵심 원칙:** 수정을 시도하기 전에 **항상** 근본 원인을 찾는다. 증상만 고치는 것은 실패다.

**이 프로세스의 문자를 어기는 것은 디버깅의 정신을 어기는 것이다.**

## 철칙 (The Iron Law)

```
근본 원인 조사 없이 수정 없음
```

1단계를 완료하지 않았다면 수정안을 제시할 수 없다.

## 언제 쓰나

모든 기술적 문제에:
- 테스트 실패
- 프로덕션 버그
- 예상치 못한 동작
- 성능 문제
- 빌드 실패
- 통합 문제

**특히 다음과 같을 때:**
- 시간 압박이 있을 때 (급할수록 추측이 유혹적이다)
- "빠른 수정 하나면 될 것 같을" 때
- 이미 여러 수정을 시도했을 때
- 이전 수정이 통하지 않았을 때
- 문제를 완전히 이해하지 못했을 때

**다음일 때도 건너뛰지 않는다:**
- 문제가 단순해 보임 (단순한 버그에도 근본 원인이 있다)
- 급함 (서두르면 재작업이 보장된다)
- 관리자가 지금 당장 원함 (체계적인 쪽이 허둥대는 것보다 빠르다)

## 네 단계

각 단계를 완료해야 다음으로 넘어갈 수 있다.

### 1단계: 근본 원인 조사

**어떤 수정이든 시도하기 전에:**

1. **에러 메시지를 꼼꼼히 읽는다**
   - 에러나 경고를 건너뛰지 않는다
   - 정확한 해결책이 거기 들어 있는 경우가 많다
   - 스택 트레이스를 끝까지 읽는다
   - 줄 번호, 파일 경로, 에러 코드를 기록한다

2. **일관되게 재현한다**
   - 확실하게 유발할 수 있는가?
   - 정확한 절차는?
   - 매번 발생하는가?
   - 재현되지 않으면 → 추측하지 말고 데이터를 더 모은다

3. **최근 변경을 확인한다**
   - 이것을 유발할 만한 무엇이 바뀌었나?
   - git diff, 최근 커밋
   - 새 의존성, 설정 변경
   - 환경 차이

4. **다중 컴포넌트 시스템에서는 증거를 모은다**

   **시스템에 여러 컴포넌트가 있을 때** (CI → 빌드 → 서명, API → 서비스 → DB):

   **수정안을 제시하기 전에 진단 계측을 추가한다:**
   ```
   각 컴포넌트 경계마다:
     - 컴포넌트로 들어가는 데이터를 로깅
     - 컴포넌트에서 나오는 데이터를 로깅
     - 환경/설정 전파를 검증
     - 각 계층의 상태를 확인

   한 번 실행해서 어디서 깨지는지 보여주는 증거를 모은다
   그다음 증거를 분석해 실패 컴포넌트를 특정한다
   그다음 그 컴포넌트를 조사한다
   ```

   다층 시스템 예시:
   ```bash
   # 계층 1: 워크플로
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 계층 2: 빌드 스크립트
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 계층 3: 서명 스크립트
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 계층 4: 실제 서명
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **이것이 드러내는 것:** 어느 계층이 실패하는가 (secrets → workflow ✓, workflow → build ✗)

5. **데이터 흐름을 추적한다**

   **에러가 콜 스택 깊숙이 있을 때:** 완전한 역추적 기법은 원문 디렉터리의 `root-cause-tracing.md`를 참고한다.

   간단 버전:
   - 잘못된 값이 어디서 생겨났나?
   - 무엇이 잘못된 값으로 이것을 호출했나?
   - 원천을 찾을 때까지 위로 계속 추적한다
   - 증상이 아니라 원천에서 고친다

### 2단계: 패턴 분석

**고치기 전에 패턴을 찾는다:**

1. **작동하는 예시를 찾는다**
   - 같은 코드베이스에서 유사하게 작동하는 코드를 찾는다
   - 깨진 것과 비슷한데 작동하는 것은 무엇인가?

2. **레퍼런스와 비교한다**
   - 어떤 패턴을 구현 중이라면 레퍼런스 구현을 **완독**한다
   - 훑지 말고 한 줄씩 읽는다
   - 적용하기 전에 패턴을 완전히 이해한다

3. **차이를 식별한다**
   - 작동하는 것과 깨진 것의 차이는?
   - 아무리 사소해도 모든 차이를 나열한다
   - "그게 영향을 줄 리 없어"라고 가정하지 않는다

4. **의존성을 이해한다**
   - 이것이 필요로 하는 다른 컴포넌트는?
   - 어떤 설정, 구성, 환경이 필요한가?
   - 어떤 가정을 하고 있는가?

### 3단계: 가설과 검증

**과학적 방법:**

1. **가설 하나를 세운다**
   - 명확하게 진술한다: "Y이기 때문에 X가 근본 원인이라고 생각한다"
   - 적어둔다
   - 모호하지 않고 구체적으로

2. **최소한으로 검증한다**
   - 가설을 검증할 **가장 작은** 변경을 한다
   - 한 번에 한 변수
   - 여러 가지를 동시에 고치지 않는다

3. **계속하기 전에 확인한다**
   - 됐는가? 예 → 4단계
   - 안 됐는가? **새로운** 가설을 세운다
   - 그 위에 수정을 덧붙이지 않는다

4. **모를 때는**
   - "X를 이해하지 못하겠다"고 말한다
   - 아는 척하지 않는다
   - 도움을 요청한다
   - 더 조사한다

### 4단계: 구현

**증상이 아니라 근본 원인을 고친다:**

1. **실패하는 테스트 케이스를 만든다**
   - 가능한 가장 단순한 재현
   - 가능하면 자동화된 테스트
   - 프레임워크가 없으면 일회성 스크립트
   - 고치기 **전에** 반드시 있어야 한다
   - 제대로 된 실패 테스트 작성에는 `superpowers:test-driven-development` 스킬을 쓴다

2. **단일 수정을 구현한다**
   - 식별한 근본 원인을 해결한다
   - 한 번에 한 변경
   - "온 김에" 개선 없음
   - 리팩터링을 끼워 넣지 않음

3. **수정을 검증한다**
   - 이제 테스트가 통과하는가?
   - 다른 테스트가 깨지지 않았는가?
   - 문제가 실제로 해결됐는가?
   - 성공을 주장하기 전에 `superpowers:verification-before-completion` 스킬을 쓴다

4. **수정이 통하지 않으면**
   - 멈춘다
   - 센다: 수정을 몇 번 시도했는가?
   - 3회 미만이면: 1단계로 돌아가 새 정보로 재분석
   - **3회 이상이면: 멈추고 아키텍처를 의심한다 (아래 5번)**
   - 아키텍처 논의 없이 4번째 수정을 시도하지 않는다

5. **수정 3회 이상 실패: 아키텍처를 의심한다**

   아키텍처 문제를 가리키는 패턴:
   - 수정할 때마다 다른 곳에서 새로운 공유 상태/결합/문제가 드러난다
   - 수정하려면 "대규모 리팩터링"이 필요하다
   - 수정할 때마다 다른 곳에 새 증상이 생긴다

   **멈추고 근본을 의심한다:**
   - 이 패턴이 근본적으로 타당한가?
   - 단지 관성으로 이것을 고수하고 있는가?
   - 증상을 계속 고치는 대신 아키텍처를 리팩터링해야 하는가?

   **추가 수정을 시도하기 전에 사람 파트너와 논의한다.**

   이것은 가설 실패가 아니다 — 잘못된 아키텍처다.

## 위험 신호 — 멈추고 프로세스를 따를 것

다음과 같은 생각이 든다면:
- "일단 빨리 고치고 나중에 조사하자"
- "그냥 X를 바꿔보고 되는지 보자"
- "여러 개 바꾸고 테스트 돌리자"
- "테스트는 건너뛰고 수동으로 확인하자"
- "아마 X일 거야, 그것부터 고치자"
- "완전히 이해하진 못했지만 이게 될 수도 있어"
- "패턴은 X라는데 나는 다르게 각색할래"
- "주요 문제는 다음과 같습니다: [조사 없이 수정안 나열]"
- 데이터 흐름을 추적하기 전에 해결책 제시
- **"한 번만 더 시도해보자" (이미 2번 이상 했을 때)**
- **수정할 때마다 다른 곳에서 새 문제가 드러남**

**전부 같은 뜻이다: 멈춰라. 1단계로 돌아가라.**

**3회 이상 실패했다면:** 아키텍처를 의심하라 (4단계 5번).

## 잘못하고 있다는 사람 파트너의 신호

다음과 같은 교정을 주의한다:
- "그게 안 일어나고 있어?" — 검증 없이 가정했다
- "그게 우리에게 보여줄까?" — 증거 수집을 추가했어야 했다
- "추측 그만해" — 이해 없이 수정을 제시하고 있다
- "울트라씽크해봐" — 증상이 아니라 근본을 의심하라
- "우리 막혔어?" (짜증 섞인) — 네 접근이 통하지 않고 있다

**이런 신호가 보이면: 멈추고 1단계로.**

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "문제가 단순해서 프로세스가 필요 없어" | 단순한 문제에도 근본 원인이 있다. 단순한 버그에는 프로세스도 빠르다. |
| "비상 상황이라 프로세스 쓸 시간 없어" | 체계적 디버깅이 추측-확인 허둥댐보다 **빠르다**. |
| "일단 이것만 해보고 조사하자" | 첫 수정이 패턴을 만든다. 처음부터 제대로 하라. |
| "수정이 되는지 확인하고 테스트 쓸게" | 테스트 없는 수정은 유지되지 않는다. 테스트 우선이 그것을 증명한다. |
| "여러 개 동시에 고치면 시간 절약" | 무엇이 통했는지 분리할 수 없다. 새 버그를 만든다. |
| "레퍼런스가 너무 길어서 패턴만 각색할게" | 부분적 이해는 버그를 보장한다. 완독하라. |
| "문제가 보이니 고치자" | 증상을 보는 것 ≠ 근본 원인을 이해하는 것. |
| "한 번만 더" (2회 이상 실패 후) | 3회 이상 실패 = 아키텍처 문제. 다시 고치지 말고 패턴을 의심하라. |

## 빠른 참조

| 단계 | 주요 활동 | 성공 기준 |
|---|---|---|
| **1. 근본 원인** | 에러 판독, 재현, 변경 확인, 증거 수집 | 무엇이 왜 일어나는지 이해 |
| **2. 패턴** | 작동 예시 찾기, 비교 | 차이 식별 |
| **3. 가설** | 이론 수립, 최소 검증 | 확인 또는 새 가설 |
| **4. 구현** | 테스트 작성, 수정, 검증 | 버그 해결, 테스트 통과 |

## "근본 원인이 없다"고 나올 때

체계적 조사 결과 문제가 정말 환경적·타이밍 의존적·외부 요인이라면:

1. 프로세스를 완료한 것이다
2. 무엇을 조사했는지 문서화한다
3. 적절한 처리를 구현한다 (재시도, 타임아웃, 에러 메시지)
4. 향후 조사를 위한 모니터링/로깅을 추가한다

**단:** "근본 원인 없음" 사례의 95%는 불완전한 조사다.

## 보조 기법

원문 디렉터리에 함께 들어 있는 기법 문서:

- **`root-cause-tracing.md`** — 콜 스택을 거슬러 올라가 최초 트리거를 찾는다
- **`defense-in-depth.md`** — 근본 원인을 찾은 후 여러 계층에 검증을 추가한다
- **`condition-based-waiting.md`** — 임의의 타임아웃을 조건 폴링으로 대체한다
- **`find-polluter.sh`** — 다른 테스트를 오염시키는 테스트를 찾는다
