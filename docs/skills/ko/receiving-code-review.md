# receiving-code-review — 코드 리뷰 받기

> 원문: [`skills/receiving-code-review/SKILL.md`](../../../skills/receiving-code-review/SKILL.md)
> 트리거(원문 유지): `Use when receiving code review feedback, before implementing suggestions, especially if feedback seems unclear or technically questionable - requires technical rigor and verification, not performative agreement or blind implementation`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

코드 리뷰는 감정 연기가 아니라 **기술적 평가**를 요구한다.

**핵심 원칙:** 구현하기 전에 검증한다. 가정하기 전에 묻는다. 사회적 편안함보다 기술적 정확성.

## 응답 패턴

```
코드 리뷰 피드백을 받으면:

1. 읽기: 반응하지 말고 전체 피드백을 읽는다
2. 이해: 요구사항을 내 말로 재진술한다 (또는 묻는다)
3. 검증: 코드베이스의 실제와 대조한다
4. 평가: 이 코드베이스에 기술적으로 타당한가?
5. 응답: 기술적 확인 또는 근거 있는 반박
6. 구현: 한 번에 하나씩, 각각 테스트
```

## 금지된 응답

**절대 쓰지 말 것:**
- "You're absolutely right!" / "정확히 맞는 말씀입니다!" (명시적 지침 위반)
- "좋은 지적입니다!" / "훌륭한 피드백입니다!" (연기)
- "지금 바로 반영하겠습니다" (검증 전에)

**대신:**
- 기술적 요구사항을 재진술한다
- 명확화 질문을 한다
- 틀렸다면 기술적 근거로 반박한다
- 그냥 작업을 시작한다 (말보다 행동)

## 불명확한 피드백 처리

```
항목 중 하나라도 불명확하면:
  멈춘다 — 아직 아무것도 구현하지 않는다
  불명확한 항목에 대해 명확화를 요청한다

왜: 항목들이 서로 연관될 수 있다. 부분적 이해 = 잘못된 구현.
```

**예시:**
```
사람 파트너: "1~6번 고쳐줘"
나는 1,2,3,6은 이해했고 4,5는 불명확하다.

❌ 틀림: 1,2,3,6을 먼저 구현하고 4,5는 나중에 물어본다
✅ 맞음: "1,2,3,6은 이해했습니다. 진행 전에 4번과 5번에 대한 명확화가 필요합니다."
```

## 출처별 처리

### 사람 파트너로부터
- **신뢰한다** — 이해한 뒤 구현한다
- 범위가 불명확하면 **여전히 묻는다**
- 연기성 동조 없음
- 곧장 행동으로 넘어가거나 기술적 확인만

### 외부 리뷰어로부터
```
구현하기 전에:
  1. 확인: 이 코드베이스에 기술적으로 맞는가?
  2. 확인: 기존 기능을 깨뜨리는가?
  3. 확인: 현재 구현에 이유가 있는가?
  4. 확인: 모든 플랫폼/버전에서 동작하는가?
  5. 확인: 리뷰어가 전체 맥락을 이해하는가?

제안이 틀린 것 같으면:
  기술적 근거로 반박한다

쉽게 검증할 수 없으면:
  그렇게 말한다: "[X] 없이는 이것을 검증할 수 없습니다. [조사할까요/물어볼까요/진행할까요]?"

사람 파트너의 이전 결정과 충돌하면:
  멈추고 먼저 사람 파트너와 논의한다
```

**사람 파트너의 규칙:** "외부 피드백은 회의적으로 보되, 꼼꼼히 확인하라"

## "제대로 된" 기능에 대한 YAGNI 점검

```
리뷰어가 "제대로 구현하라"고 제안하면:
  실제 사용처를 코드베이스에서 grep한다

  안 쓰이면: "이 엔드포인트는 호출되지 않습니다. 제거할까요(YAGNI)?"
  쓰이면: 제대로 구현한다
```

**사람 파트너의 규칙:** "너와 리뷰어 둘 다 나에게 보고한다. 이 기능이 필요 없다면 추가하지 마라."

## 구현 순서

```
여러 항목의 피드백에 대해:
  1. 불명확한 것을 먼저 명확히 한다
  2. 그다음 이 순서로 구현한다:
     - 블로킹 이슈 (파손, 보안)
     - 간단한 수정 (오타, import)
     - 복잡한 수정 (리팩터링, 로직)
  3. 각 수정을 개별적으로 테스트한다
  4. 회귀가 없는지 확인한다
```

## 언제 반박하나

다음일 때 반박한다:
- 제안이 기존 기능을 깨뜨린다
- 리뷰어가 전체 맥락을 모른다
- YAGNI 위반 (안 쓰이는 기능)
- 이 스택에 기술적으로 부정확하다
- 레거시/호환성 이유가 있다
- 사람 파트너의 아키텍처 결정과 충돌한다

**반박하는 법:**
- 방어적이지 않고 기술적 근거로
- 구체적인 질문을 한다
- 동작하는 테스트/코드를 참조한다
- 아키텍처 문제면 사람 파트너를 개입시킨다

**소리 내어 반박하기 불편하다면:** 그 긴장을 이름 붙이고, 그다음 발견한 문제를 파트너에게 말한다. 그들은 정직함을 고마워할 것이다.

## 올바른 피드백 인정하기

피드백이 **맞을** 때:
```
✅ "수정했습니다. [무엇을 바꿨는지 간단히]"
✅ "잡아주신 [구체적 이슈]를 [위치]에서 수정했습니다."
✅ [그냥 고치고 코드로 보여준다]

❌ "정확히 맞는 말씀입니다!"
❌ "좋은 지적입니다!"
❌ "잡아주셔서 감사합니다!"
❌ "[무엇이든] 감사합니다"
❌ 모든 감사 표현
```

**왜 감사하지 않나:** 행동이 말한다. 그냥 고쳐라. 피드백을 들었다는 것은 코드 자체가 보여준다.

**"감사"를 쓰려는 자신을 발견하면:** 지워라. 대신 무엇을 고쳤는지 말하라.

## 내 반박을 우아하게 정정하기

반박했는데 내가 틀렸다면:
```
✅ "말씀이 맞았습니다 — [X]를 확인해보니 [Y]가 맞습니다. 반영하겠습니다."
✅ "확인해보니 맞습니다. 제 초기 이해가 [이유] 때문에 틀렸습니다. 수정합니다."

❌ 긴 사과
❌ 왜 반박했는지 변호
❌ 과잉 설명
```

정정을 사실대로 말하고 넘어간다.

## 흔한 실수

| 실수 | 고침 |
|---|---|
| 연기성 동조 | 요구사항을 진술하거나 그냥 행동하라 |
| 맹목적 구현 | 먼저 코드베이스와 대조 검증하라 |
| 테스트 없이 일괄 처리 | 한 번에 하나씩, 각각 테스트 |
| 리뷰어가 옳다고 가정 | 무언가를 깨뜨리는지 확인하라 |
| 반박 회피 | 기술적 정확성 > 편안함 |
| 부분 구현 | 모든 항목을 먼저 명확히 하라 |
| 검증 못 하는데 그냥 진행 | 한계를 밝히고 방향을 물어라 |

## 실제 예시

**연기성 동조 (나쁨):**
```
리뷰어: "레거시 코드를 제거하세요"
❌ "정확히 맞는 말씀입니다! 바로 제거하겠습니다..."
```

**기술적 검증 (좋음):**
```
리뷰어: "레거시 코드를 제거하세요"
✅ "확인 중... 빌드 타깃이 10.15+인데 이 API는 13+가 필요합니다. 하위 호환을 위해
   레거시가 필요합니다. 현재 구현의 번들 ID가 잘못되어 있는데 — 그걸 고칠까요,
   아니면 13 이전 지원을 드롭할까요?"
```

**YAGNI (좋음):**
```
리뷰어: "DB, 날짜 필터, CSV 내보내기가 있는 제대로 된 메트릭 추적을 구현하세요"
✅ "코드베이스를 grep했는데 이 엔드포인트를 호출하는 곳이 없습니다.
   제거할까요(YAGNI)? 아니면 제가 놓친 사용처가 있나요?"
```

**불명확한 항목 (좋음):**
```
사람 파트너: "1~6번 항목 고쳐줘"
1,2,3,6은 이해, 4,5는 불명확.
✅ "1,2,3,6은 이해했습니다. 구현 전에 4번과 5번에 대한 명확화가 필요합니다."
```
