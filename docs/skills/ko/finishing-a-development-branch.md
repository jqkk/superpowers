# finishing-a-development-branch — 개발 브랜치 마무리

> 원문: [`skills/finishing-a-development-branch/SKILL.md`](../../../skills/finishing-a-development-branch/SKILL.md)
> 트리거(원문 유지): `Use when implementation is complete, all tests pass, and you need to decide how to integrate the work`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

**핵심 원칙:** 테스트 검증 → 환경 감지 → 선택지 제시 → 선택 실행 → 정리.

**시작할 때 선언:** "finishing-a-development-branch 스킬을 사용해 이 작업을 마무리합니다."

## 1단계: 테스트 검증

프로젝트의 전체 테스트 스위트를 실행한다 (`npm test` / `cargo test` / `pytest` / `go test ./...`).

**테스트가 실패하면** 실패를 보고하고 멈춘다 — 메뉴는 스위트가 green이 된 뒤에 나온다:

```
테스트 실패 (<N>건). 완료 전에 수정해야 합니다:

[실패 내역]
```

**테스트가 통과하면:** 2단계로.

## 2단계: 환경 감지

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
# 아직 워크스페이스 안에 있을 때 잡아둔다 — 5단계에서 디렉터리를 바꾸는데
# 6단계 정리에 이 값이 필요하다
WORKTREE_PATH=$(git rev-parse --show-toplevel)
```

이것이 어떤 메뉴를 보여줄지와 정리 방식을 결정한다:

| 상태 | 메뉴 | 정리 |
|---|---|---|
| `GIT_DIR == GIT_COMMON` (일반 저장소) | 표준 3개 옵션 | 정리할 워크트리 없음 |
| `GIT_DIR != GIT_COMMON`, 이름 있는 브랜치 | 표준 3개 옵션 | 출처 기반 (6단계 참고) |
| `GIT_DIR != GIT_COMMON`, detached HEAD | 축소된 2개 옵션 (머지 제외) | 외부 관리 — 그대로 둔다 |

## 3단계: 기준 브랜치 결정

기준 브랜치는 이 작업이 분기해 나온 곳이다 — 보통 계획, 대화, 또는 브랜치의 upstream에 이름이 있다. 이미 알려져 있지 않다면 묻는다: "이 브랜치는 <내 최선의 추측>에서 갈라진 것 같은데, 맞나요?" **머지 전에 확인한다** — 잘못된 기준으로 머지하면 되돌리는 비용이 크다.

## 4단계: 선택지 제시

**일반 저장소와 이름 있는 브랜치 워크트리 — 정확히 이 3개 옵션을 제시한다:**

```
구현이 완료되었습니다. 어떻게 할까요?

1. <기준 브랜치>로 로컬 머지
2. 푸시하고 Pull Request 생성
3. 브랜치를 그대로 두기 (나중에 직접 처리)

어느 것으로 할까요?
```

**detached HEAD — 정확히 이 2개 옵션을 제시한다:**

```
구현이 완료되었습니다. 현재 detached HEAD 상태입니다 (외부에서 관리되는 워크스페이스).

1. 새 브랜치로 푸시하고 Pull Request 생성
2. 그대로 두기 (나중에 직접 처리)

어느 것으로 할까요?
```

메뉴는 **쓰인 그대로** 제시한다 — 간결하게, 모든 옵션은 위 목록에서 나온다. **작업을 폐기하는 것은 사람 파트너가 명시적으로 요청할 때만** 일어난다(아래 "사람 파트너가 폐기를 요청하면" 참고). 그들의 답을 기다린다 — 통합 결정은 그들의 것이다.

## 5단계: 선택 실행

### 옵션 1: 로컬 머지

```bash
# CWD 안전을 위해 메인 저장소 루트를 얻는다
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"

# 먼저 머지 — 무엇을 제거하기 전에 성공을 확인한다
git checkout <기준-브랜치>
git pull
git merge <기능-브랜치>

# 머지 결과에 대해 테스트를 검증한다
<테스트 명령>
```

머지 결과에서 테스트가 실패하면: 멈추고, 워크트리와 브랜치를 그대로 두고, 조사한다. 아무것도 푸시되지 않았으므로 머지는 로컬이고 복구 가능하다.

머지 결과가 green이 되면: 워크트리를 정리하고(6단계), 그다음 브랜치를 삭제한다:

```bash
git branch -d <기능-브랜치>
```

### 옵션 2: 푸시하고 PR 생성

```bash
git push -u origin <기능-브랜치>
# detached HEAD에서는 원격에 새 브랜치 이름을 지정한다:
# git push origin HEAD:refs/heads/<새-브랜치>
```

그다음 포지의 도구로 <기준 브랜치>를 향한 pull/merge request를 생성한다 — CLI가 있으면 그것으로, 아니면 푸시할 때 대부분의 포지가 출력하는 생성 URL로 — 저장소의 PR 템플릿과 관례가 있으면 따르고, URL을 사람 파트너에게 보고한다.

**워크트리는 유지한다** — 파트너가 PR 피드백을 거기서 반영한다.

### 옵션 3: 그대로 두기

보고한다: "브랜치 <이름>을 유지합니다. 워크트리는 <경로>에 보존되었습니다."

### 사람 파트너가 폐기를 요청하면

이 경로는 **작업을 버려 달라는 명시적 요청에 대한 응답으로만** 존재한다. 먼저 확인한다:

```
다음이 영구히 삭제됩니다:
- 브랜치 <이름>
- 모든 커밋: <커밋 목록>
- 워크트리 <경로>

확인하려면 'discard'를 입력하세요.
```

그 정확한 확인을 기다린다. 도착하면:

```bash
MAIN_ROOT=$(git -C "$(git rev-parse --git-common-dir)/.." rev-parse --show-toplevel)
cd "$MAIN_ROOT"
```

그다음 워크트리를 정리하고(6단계) 브랜치를 강제 삭제한다:

```bash
git branch -D <기능-브랜치>
```

## 6단계: 워크스페이스 정리

**옵션 1과 확인된 폐기에서만 실행된다.** 옵션 2와 3은 항상 워크트리를 보존한다. 두 호출자 모두 이미 메인 저장소 루트로 디렉터리를 옮겼고(워크트리 제거는 워크트리 밖에서 실행되어야 한다) 그 이동 전에 2단계에서 잡아둔 `GIT_DIR`/`GIT_COMMON`/`WORKTREE_PATH` 값을 쓴다.

**`GIT_DIR == GIT_COMMON`이면:** 일반 저장소, 정리할 워크트리 없음. 끝.

**`WORKTREE_PATH`가 `.worktrees/` 또는 `worktrees/` 아래이면:** Superpowers가 이 워크트리를 만들었으므로 정리는 우리 몫이다:

```bash
git worktree remove "$WORKTREE_PATH"
git worktree prune  # 자가 치유: 오래된 등록을 정리
```

**제거가 거부되면**(`contains modified or untracked files`): 그 워크트리에는 **다른 어디에도 없는 파일** — 커밋되지 않은 계획, 노트, 스크래치 — 이 들어 있다. 내 판단으로 `--force`를 쓰지 않는다. 무엇이 걸려 있는지 파트너에게 보여주고 묻는다:

```bash
git -C "$WORKTREE_PATH" status --porcelain -uall
```

```
워크트리 제거가 거부되었습니다 — 다음 파일들은 커밋된 적이 없습니다:

<파일 목록>

1. 정리 전에 <브랜치>에 커밋
2. <메인 저장소 루트>로 이동
3. 삭제 (복구 불가)

어느 것으로 할까요?
```

선택을 수행한 뒤 워크트리를 제거한다.

**그 외:** 호스트 환경이 이 워크스페이스를 소유한다 — 그대로 둔다. 플랫폼이 워크스페이스 종료 도구를 제공하면 그것을 쓴다.

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "이번 세션 초반에 테스트 통과했어" | 통합하려는 바로 그 트리에 대해 스위트를 돌려라. green 실행은 그것이 돌아간 트리만 증명한다. |
| "당연히 머지를 원하겠지" | 통합은 사람 파트너의 결정이다. 메뉴를 제시하고 기다려라. |
| "이 기능은 끝난 것 같으니 폐기를 제안하자" | 메뉴는 쓰인 그대로 완결되어 있다. 폐기는 파트너가 그렇게 말할 때만 일어난다. |
| "'응, 그거 없애줘'면 확인된 거지" | 타이핑된 `discard`만이 삭제를 승인한다. |
| "PR 올렸으니 워크트리는 이제 쓰레기야" | PR 피드백은 그 워크트리에서 반영된다. 작업이 착지할 때까지 남는다. |
| "이 다른 워크트리는 오래돼 보이니 같이 치우자" | `.worktrees/` 또는 `worktrees/` 아래 워크트리만 정리한다. 나머지는 호스트의 것이다. |
| "제거 거부됐네, `--force`로 마무리하면 되지" | 거부는 그 파일들이 그 워크트리에만 존재한다는 뜻이다. `--force`는 영구 파괴다. 파트너에게 보여주고 물어라. |
| "머지 결과 실패는 아마 flaky일 거야" | 머지 결과 실패는 모든 것을 멈춘다. 조사하는 동안 브랜치와 워크트리는 그대로 둔다. |
| "기준 브랜치는 당연히 main이지" | 분기 지점을 확인하거나 물어라. 잘못된 기준으로 머지하면 되돌리기 비싸다. |
| "푸시가 거부됐으니 force-push로 해결하자" | 거부는 원격이 움직였다는 뜻이다. 조사하라. force-push는 파트너의 명시적 요청 시에만. |
