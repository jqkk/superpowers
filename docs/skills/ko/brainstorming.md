# brainstorming — 아이디어를 설계로

> 원문: [`skills/brainstorming/SKILL.md`](../../../skills/brainstorming/SKILL.md)
> 트리거(원문 유지): `You MUST use this before any creative work - creating features, building components, adding functionality, or modifying behavior. Explores user intent, requirements and design before implementation.`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

자연스러운 협업 대화를 통해 아이디어를 완성된 설계와 스펙으로 바꾸도록 돕는다.

먼저 이 요청에 얼마나 많은 프로세스가 필요한지 분류하고, 선택한 경로를 따라 진행한다: 맥락 이해 → 아이디어 정제 → 설계 제시 → 사람 파트너의 승인.

## 공통의 이해 확립

브레인스토밍의 결과물은 사람 파트너가 알아보고 교정할 수 있는 이해이며, 그들이 무엇을 달성하려는지에 뿌리를 둔다.

1. **의도를 발견한다.** 요청과 가용한 맥락으로부터 의도한 결과, 대상, 성공의 모습을 파악한다. 그 정보가 없다면, 기능이나 접근을 제안하기 전에 목적이나 용도에 관한 집중된 질문을 하나 한다. 앱의 장르를 아는 것이 파트너가 **왜** 그것을 원하는지 알려주지는 않는다. 빠진 요구사항을 모으는 것은 작업을 다시 승인해 달라는 요청이 아니다.
2. **이해한 바를 되돌려 쓴다.** 의도한 결과, 관련 제약, 성공 기준을 파트너가 평가할 수 있는 짧은 노트로 요약한다. 그들이 말한 것과 내 가정을 구분한다. 교정을 청하고, 그 답을 반영한 뒤에야 이것을 설계 브리프로 삼는다.
3. **의도를 설계로 옮긴다.** 합의된 이해를 선택한 경로의 설계 산출물에 보존한다: 아키텍처 작업이면 작성된 스펙에, 한정된 작업이나 스파이크면 채팅 내 설계/프로브에. 제안하는 기능과 기술 선택을 그 이해에 비추어 점검한다.

요청이 이미 목적과 제약을 제공한다면 같은 질문을 반복하지 말고 이해한 바를 되비춘다. 노트는 간결하게 — 중요한 것은 정확성과 교정할 기회다.

<하드-게이트>
구현 스킬 호출, 프로덕트 코드 작성, 스캐폴딩, 프로덕트 의존성 설치, 외부 프로젝트 생성을 포함한 **어떤 구현 행동을 하기 전에** 선택한 경로의 선행 조건을 완료한다:

- **스파이크:** 사람 파트너가 질문과 프로브를 승인한다.
- **한정(Bounded):** 사람 파트너가 채팅 내 짧은 설계를 승인한다.
- **아키텍처:** 사람 파트너가 작성된 스펙을 검토·승인하고, 그다음 작성된 구현 계획을 검토하고 실행 방식을 선택한다. 대화상의 설계 승인은 스펙을 **쓰는 것**만 허용하고, 작성된 스펙의 승인은 writing-plans를 **호출하는 것**만 허용한다.

답변은 **실제로 제시된 단계**를 승인한다. 아이디어나 기능 범위의 승인이 아직 존재하지도 않는 산출물을 승인하는 것은 아니다. 가장 이른 미완료 단계에서 재개한다. 하나의 승인을 나머지를 건너뛸 허가로 바꾸지 않는다. 그 선행 조건이 미완료인 동안 읽기 전용 프로젝트 탐색은 허용된다.
</하드-게이트>

## 세 가지 경로

첫 질문을 하기 전에 요청을 분류하고 그 분류를 **소리내어 말한다** — "이건 한정된 작업으로 보이니 스펙을 쓰는 대신 여기서 짧은 설계를 제시하겠습니다" — 그래야 사람 파트너가 뒤집을 수 있다.

- **스파이크(Spike)** — 타당성 질문("가능할까", "될까", "일단 대충이라도"). 결과물은 **답**이지 보관할 코드가 아니다. 질문과 시도할 내용을 2~3문장으로 제시하고, 동의를 받고, 정확성이 허락하는 한 가장 싸게 알아낸다. 설계 문서도, 스펙 파일도 없다. 결과는 권고로 보고하고, 만든 것은 무엇이든 **버릴 것**이라고 명시한다.
- **한정(Bounded)** — 이 저장소에 **이미 존재하는** 코드에 대한 범위가 명확한 변경: 새 플래그, 작은 엔드포인트, 한 파일 수정. 앱의 종류를 이해하는 것으로는 부족하다 — 한정이란 **변경하려는 흐름이 이미 읽을 수 있게 여기 있다**는 뜻이다. 변경할 기존 흐름이 없다면 한정된 작업이 아니다. 중요한 명확화 질문을 하고, **채팅 안에** 짧은 설계(몇 문장에서 짧은 몇 문단)를 제시하고, **멈춘다**. 구현은 사람 파트너가 그 설계에 yes라고 한 뒤에만 시작한다 — 한정된 작업의 승인도 아키텍처만큼 단단한 게이트다. 스펙 파일도, 구현 계획 문서도 없다.
- **아키텍처(Architectural)** — 새 프로젝트, 새 서브시스템, 컴포넌트들이 맞물리는 방식을 재구성하거나 다른 곳이 의존하는 인터페이스를 바꾸는 변경. 전체 프로세스를 따른다: 질문, 접근안, 섹션별 설계, 작성된 스펙, 그다음 writing-plans 스킬.

두 경로 사이에서 망설여지면 **더 무거운 쪽**을 택한다. 래칫은 단방향이다 — 작업 중에 발견된 숨은 복잡도는 경로를 **올린다**. 멈추고, 그렇게 말하고, 한 단계 올라간다. 작업 중에 내려가는 일은 없다.

## 안티패턴: "승인이 필요 없을 만큼 단순하다"

모든 경로는 구현 전에 사람 파트너가 필요한 설계를 승인하는 것으로 끝난다. 한정된 변경은 채팅 두 문장이면 될 수도 있다. 새 todo 리스트 프로젝트는 아키텍처이고 작성된 스펙과 계획 인계가 필요하다. 산출물을 선택한 경로에 맞게 조절하되, 구현 전에 그 경로의 검토를 완료한다.

## 위험 신호

| 생각 | 실제 |
|---|---|
| "설계가 필요 없을 만큼 단순해" | 선택한 경로를 따르라: 한정된 변경은 짧은 채팅 설계를, 아키텍처 변경은 작성된 스펙과 계획 인계를 받는다. |
| "한정이라고 부르고 스펙을 건너뛰자" | 일을 건너뛰려고 라벨에 손을 뻗는 것 자체가 그 의심이다 — 더 무거운 경로를 택하라. |
| "한정이고 설계가 뻔하니, 그들이 읽는 동안 시작하자" | 게이트는 설계의 길이가 아니라 승인이다. 제시하고, yes를 들을 때까지 멈춰라. |
| "이런 종류의 앱을 아니까 한정이다" | 한정은 네 친숙함이 아니라 저장소를 기준으로 한다. 새 프로젝트에는 기존 흐름이 없다 — 아키텍처다. |
| "스파이크가 되니까 코드를 남기자" | 스파이크의 결과물은 답이다. 코드를 남기는 것은 새 요청이다 — 분류하라. |
| "커지긴 했지만 거의 다 됐으니 재분류는 생략" | 숨은 복잡도는 작업 중에 경로를 올린다. 멈추고 말하라. |
| "스파이크를 승인했으니 후속 변경도 승인된 것" | 모든 작업은 자기만의 분류와 자기만의 승인을 받는다. |

## 체크리스트

먼저 분류하고, 경로를 선언하고, 그 경로의 항목마다 태스크를 만들어 순서대로 완료한다.

**스파이크:**
1. **프로젝트 맥락 탐색** — 프로브를 구성할 만큼만
2. **질문 + 프로브 계획 제시** — 2~3문장
3. **승인 받기** — 끄덕임이면 충분
4. **조사** — 정확성이 허락하는 한 싸게
5. **결과 보고** — 권고; 만든 것은 버릴 것이라고 명시

**한정:**
1. **프로젝트 맥락 탐색** — 파일, 문서, 최근 커밋 확인
2. **명확화 질문** — 한 번에 하나씩, 중요한 것만
3. **채팅에 짧은 설계 제시** — 접근, 건드릴 파일, 테스트 방법
4. **승인 받기** — 멈추고 명시적인 yes를 기다린다. 설계를 제시하면서 같은 호흡에 시작하는 것은 게이트를 건너뛰는 것이다
5. **구현** — 일반 개발 워크플로로 진행(TDD 적용). 계획 문서는 없다

**아키텍처:**
1. **프로젝트 맥락 탐색** — 파일, 문서, 최근 커밋 확인
2. **비주얼 컴패니언을 적시에 제안** — 미리 하지 않는다. 설명보다 보여주는 게 진짜로 명확할 질문이 처음 나올 때 그때 제안한다(단독 메시지로). 승인하면 브라우저 탭이 열린다. 시각적 질문이 끝내 없다면 절대 제안하지 않는다. 아래 비주얼 컴패니언 절 참고
3. **명확화 질문** — 한 번에 하나씩, 목적/제약/성공 기준을 이해
4. **2~3개 접근안 제안** — 트레이드오프와 내 추천과 함께
5. **설계 제시** — 복잡도에 맞춘 섹션별로, 섹션마다 사용자 승인을 받는다
6. **설계 문서 작성** — `docs/superpowers/specs/YYYY-MM-DD-<주제>-design.md`에 저장하고 커밋
7. **스펙 셀프 리뷰** — 플레이스홀더, 모순, 모호함, 범위를 인라인으로 빠르게 점검
8. **사용자가 작성된 스펙을 검토** — 진행 전에 스펙 파일을 검토해 달라고 요청
9. **구현으로 전환** — writing-plans 스킬을 호출해 구현 계획을 만든다

## 프로세스 흐름

```
분류: 스파이크 / 한정 / 아키텍처
 ├─ 스파이크 → 질문+프로브(2~3문장) → 승인? → 조사 → 권고 보고 [종료]
 ├─ 한정 → 명확화 질문 → 채팅 내 짧은 설계 → 승인? → 일반 워크플로로 구현 [종료]
 └─ 아키텍처 → 맥락 탐색 → 명확화 질문 → 2~3개 접근안 → 섹션별 설계
                → 설계 승인? (아니면 수정 반복) → 설계 문서 작성
                → 스펙 셀프 리뷰(인라인 수정) → 사용자 스펙 검토?
                → (변경 요청이면 문서로 복귀) → writing-plans 호출 [종료]

숨은 복잡도 발견 → 경로를 올리고 다시 분류
```

**종료 상태는 경로에 묶여 있다.** 아키텍처: 브레인스토밍 이후 호출하는 스킬은 **오직 writing-plans뿐**이다 — frontend-design, mcp-builder, 그 밖의 어떤 구현 스킬도 아니다. 한정: 승인 후 일반 개발 워크플로로 곧장 구현하며, 계획 문서는 없다. 스파이크: 종료 상태는 보고된 권고다.

## 프로세스 상세

아래 절들은 한정·아키텍처 경로를 위한 것이다(스파이크는 "프로브를 제시하고 끄덕임을 받는다"에서 끝난다). **접근안 탐색**부터는 아키텍처 경로의 깊이다 — 한정된 작업에서는 맥락 + 몇 가지 질문 + 짧은 채팅 설계가 프로세스의 전부다.

**아이디어 이해하기:**

- 먼저 현재 프로젝트 상태를 확인한다 (파일, 문서, 최근 커밋)
- 세부 질문을 하기 전에 범위를 가늠한다. 요청이 여러 독립 서브시스템을 서술한다면(예: "채팅, 파일 저장, 결제, 분석이 있는 플랫폼을 만들자") 즉시 그 점을 지적한다. 먼저 분해해야 할 프로젝트의 세부를 다듬는 데 질문을 쓰지 않는다
- 프로젝트가 스펙 하나에 담기엔 너무 크면 서브 프로젝트로 분해하도록 돕는다: 독립적인 조각은 무엇인지, 어떻게 관계되는지, 어떤 순서로 만들지. 그다음 첫 서브 프로젝트를 일반 설계 흐름으로 브레인스토밍한다. 각 서브 프로젝트는 자기만의 스펙 → 계획 → 구현 사이클을 갖는다
- 적절한 범위의 프로젝트라면, 아이디어를 다듬기 위해 한 번에 하나씩 질문한다
- 가능하면 객관식 질문을 선호하되 개방형도 괜찮다
- 메시지당 질문 하나 — 한 주제에 탐색이 더 필요하면 여러 질문으로 쪼갠다
- 목적, 제약, 성공 기준을 이해하는 데 집중한다

**접근안 탐색:**

- 트레이드오프와 함께 2~3개의 다른 접근을 제안한다
- 선택지를 대화체로 제시하고 내 추천과 근거를 함께 준다
- 추천안을 먼저 제시하고 왜인지 설명한다
- YAGNI를 가차없이 — 모든 접근과 설계에서 불필요한 기능을 제거한다

**설계 제시:**

- 무엇을 만드는지 이해했다고 믿게 되면 설계를 제시한다
- 각 섹션을 복잡도에 맞게 조절한다: 단순하면 몇 문장, 미묘하면 200~300단어까지
- 섹션마다 여기까지 맞는지 묻는다
- 아키텍처, 컴포넌트, 데이터 흐름, 에러 처리, 테스트를 다룬다
- 말이 안 되는 부분이 있으면 되돌아가 명확히 할 준비를 한다

**격리와 명료성을 위한 설계:**

- 시스템을 각각 하나의 명확한 목적을 가지고, 잘 정의된 인터페이스로 소통하며, 독립적으로 이해·테스트할 수 있는 작은 단위로 나눈다
- 각 단위에 대해 답할 수 있어야 한다: 무엇을 하는가, 어떻게 쓰는가, 무엇에 의존하는가
- 내부를 읽지 않고도 그 단위가 무엇을 하는지 이해할 수 있는가? 소비자를 깨뜨리지 않고 내부를 바꿀 수 있는가? 아니라면 경계를 다듬어야 한다
- 작고 경계가 명확한 단위는 에이전트가 다루기에도 쉽다 — 한 번에 컨텍스트에 담을 수 있는 코드에 대해 더 잘 추론하고, 파일이 집중되어 있을 때 편집이 더 신뢰할 만하다. 파일이 커진다는 것은 대개 너무 많은 일을 하고 있다는 신호다

**기존 코드베이스에서 작업하기:**

- 변경을 제안하기 전에 현재 구조를 탐색한다. 기존 패턴을 따른다
- 기존 코드의 문제가 작업에 영향을 준다면(너무 커진 파일, 불명확한 경계, 뒤엉킨 책임) 설계의 일부로 표적 개선을 포함한다 — 좋은 개발자가 자기가 작업하는 코드를 개선하는 방식으로
- 관련 없는 리팩터링은 제안하지 않는다. 현재 목표에 봉사하는 것에 집중한다

## 설계 이후 (아키텍처 경로)

**문서화:**

- 검증된 설계(스펙)를 `docs/superpowers/specs/YYYY-MM-DD-<주제>-design.md`에 쓴다
  - (스펙 위치에 대한 사용자 선호가 이 기본값을 덮어쓴다)
- 가능하면 elements-of-style:writing-clearly-and-concisely 스킬을 쓴다
- 설계 문서를 git에 커밋한다

**스펙 셀프 리뷰:**
스펙 문서를 쓴 뒤 새로운 눈으로 본다:

1. **플레이스홀더 스캔:** "TBD", "TODO", 미완성 섹션, 모호한 요구사항이 있는가? 고친다
2. **내부 일관성:** 서로 모순되는 섹션이 있는가? 아키텍처가 기능 서술과 맞는가?
3. **범위 점검:** 구현 계획 하나에 담길 만큼 집중되어 있는가, 아니면 분해가 필요한가?
4. **모호성 점검:** 두 가지로 해석될 수 있는 요구사항이 있는가? 있다면 하나를 고르고 명시한다

문제는 인라인으로 고친다. 재검토할 필요 없다 — 고치고 넘어간다.

**사용자 검토 게이트:**
스펙 리뷰 루프가 통과하면, 진행 전에 사용자에게 작성된 스펙을 검토해 달라고 요청한다:

> "스펙을 작성해 `<경로>`에 커밋했습니다. 검토하시고, 구현 계획을 쓰기 전에 바꾸고 싶은 것이 있으면 알려주세요."

사용자의 응답을 기다린다. 변경을 요청하면 반영하고 스펙 리뷰 루프를 다시 돌린다. 승인한 뒤에만 진행한다.

**구현:**

- writing-plans 스킬을 호출해 상세 구현 계획을 만든다
- 다른 어떤 스킬도 호출하지 않는다. writing-plans가 다음 단계다

## 비주얼 컴패니언

브레인스토밍 중 목업, 다이어그램, 시각적 선택지를 보여주기 위한 브라우저 기반 동반 도구. **모드가 아니라 도구**다. 컴패니언을 수락했다는 것은 시각적 처리가 도움이 되는 질문에 쓸 수 있다는 뜻이지, 모든 질문이 브라우저를 거친다는 뜻이 아니다.

**제안 방법(적시에):** 미리 제안하지 **않는다**. 말로 하는 것보다 보여주는 게 진짜로 명확할 질문 — 단순히 UI *주제*가 아니라 실제 목업/레이아웃/다이어그램 질문 — 이 나올 때까지 기다린다. 그런 일이 처음 생기면 그때, 단독 메시지로 제안한다:

> "이 다음 부분은 제가 보여드리는 게 더 쉬울 것 같습니다 — 목업, 다이어그램, 비교를 브라우저 탭에 띄워가며 진행할 수 있습니다. 아직 새 기능이라 토큰을 많이 쓸 수 있습니다. 해볼까요? 제가 열어드리겠습니다."

**이 제안은 반드시 단독 메시지여야 한다.** 제안만 — 명확화 질문도, 요약도, 다른 내용도 없이. 사용자의 응답을 기다린다. 수락하면 `--open`으로 서버를 시작해 첫 화면이 자동으로 열리게 한다. 거절하면 텍스트로만 계속하고, 그들이 다시 꺼내지 않는 한 재제안하지 않는다.

**질문별 판단:** 사용자가 수락한 뒤에도 **질문마다** 브라우저를 쓸지 터미널을 쓸지 정한다. 기준: **사용자가 읽는 것보다 보는 것으로 더 잘 이해하겠는가?**

- **브라우저:** 내용 자체가 시각적인 것 — 목업, 와이어프레임, 레이아웃 비교, 아키텍처 다이어그램, 나란히 놓은 시각 디자인
- **터미널:** 내용이 텍스트인 것 — 요구사항 질문, 개념적 선택, 트레이드오프 목록, A/B/C/D 텍스트 선택지, 범위 결정

UI 주제에 관한 질문이 자동으로 시각적 질문인 것은 아니다. "이 맥락에서 personality가 무슨 뜻인가요?"는 개념적 질문이므로 터미널을 쓴다. "어느 위저드 레이아웃이 나은가요?"는 시각적 질문이므로 브라우저를 쓴다.

컴패니언에 동의하면, 진행 전에 상세 가이드를 읽는다: `skills/brainstorming/visual-companion.md`
