# test-driven-development — 테스트 주도 개발 (TDD)

> 원문: [`skills/test-driven-development/SKILL.md`](../../../skills/test-driven-development/SKILL.md)
> 트리거(원문 유지): `Use when implementing any feature or bugfix, before writing implementation code`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

테스트를 먼저 쓴다. 실패하는 것을 지켜본다. 통과시킬 최소한의 코드를 쓴다.

**핵심 원칙:** 테스트가 실패하는 것을 보지 않았다면, 그 테스트가 올바른 것을 검사하는지 알 수 없다.

**규칙의 문자를 어기는 것은 규칙의 정신을 어기는 것이다.**

## 언제 쓰나

**항상:**
- 새 기능
- 버그 수정
- 리팩터링
- 동작 변경

**예외 (사람 파트너에게 물을 것):**
- 버릴 프로토타입
- 생성된 코드
- 설정 파일

"이번만 TDD를 건너뛸까" 하는 생각이 든다면 멈춰라. 그것이 합리화다.

## 철칙 (The Iron Law)

```
실패하는 테스트 없이 프로덕션 코드 없음
```

테스트보다 코드를 먼저 썼는가? 삭제하라. 처음부터 다시 시작하라.

**예외 없음:**
- "참고용"으로 남기지 말 것
- 테스트를 쓰면서 그것을 "각색"하지 말 것
- 쳐다보지도 말 것
- 삭제는 삭제를 뜻한다

테스트로부터 새로 구현한다. 끝.

## Red-Green-Refactor

```
RED(실패 테스트 작성) → 올바르게 실패하는지 확인
  → GREEN(최소 코드) → 통과 및 전체 green 확인
  → REFACTOR(정리, green 유지) → 다음
```

### RED — 실패하는 테스트 작성

무슨 일이 일어나야 하는지 보여주는 최소한의 테스트 하나를 쓴다.

좋은 예 — 이름이 명확하고, 실제 동작을 검사하며, 한 가지만 본다:
```typescript
test('retries failed operations 3 times', async () => {
  let attempts = 0;
  const operation = () => {
    attempts++;
    if (attempts < 3) throw new Error('fail');
    return 'success';
  };

  const result = await retryOperation(operation);

  expect(result).toBe('success');
  expect(attempts).toBe(3);
});
```

나쁜 예 — 이름이 모호하고, 코드가 아니라 목(mock)을 검사한다:
```typescript
test('retry works', async () => {
  const mock = jest.fn()
    .mockRejectedValueOnce(new Error())
    .mockRejectedValueOnce(new Error())
    .mockResolvedValueOnce('success');
  await retryOperation(mock);
  expect(mock).toHaveBeenCalledTimes(3);
});
```

**요구사항:** 동작 하나 / 명확한 이름 / 실제 코드 (목은 불가피할 때만)

### RED 확인 — 실패를 지켜본다

**필수. 절대 건너뛰지 않는다.**

```bash
npm test path/to/test.test.ts
```

확인할 것:
- 테스트가 실패한다 (에러가 아니라)
- 실패 메시지가 예상한 것이다
- 기능이 없어서 실패한다 (오타 때문이 아니라)

**테스트가 통과한다면?** 이미 있는 동작을 검사하고 있는 것이다. 테스트를 고쳐라.

**테스트가 에러난다면?** 에러를 고치고, 올바르게 실패할 때까지 다시 실행하라.

### GREEN — 최소한의 코드

테스트를 통과시킬 가장 단순한 코드를 쓴다.

좋은 예 — 통과시킬 만큼만:
```typescript
async function retryOperation<T>(fn: () => Promise<T>): Promise<T> {
  for (let i = 0; i < 3; i++) {
    try {
      return await fn();
    } catch (e) {
      if (i === 2) throw e;
    }
  }
  throw new Error('unreachable');
}
```

나쁜 예 — 과잉 설계(YAGNI): `maxRetries`, `backoff`, `onRetry` 같은 옵션을 미리 만드는 것.

기능을 추가하거나, 다른 코드를 리팩터링하거나, 테스트 범위를 넘어 "개선"하지 않는다.

### GREEN 확인 — 통과를 지켜본다

**필수.**

확인할 것:
- 테스트가 통과한다
- 다른 테스트도 여전히 통과한다
- 출력이 깨끗하다 (에러·경고 없음)

**테스트가 실패하면?** 테스트가 아니라 코드를 고쳐라.
**다른 테스트가 실패하면?** 지금 고쳐라.

**"다른 테스트"는 내 파일이 아니라 프로젝트 전체 스위트를 뜻한다.** 내가 쓴 테스트가 green인 것은 스위트가 green인 것이 아니다. 변경을 완료라고 부르기 전에, 태스크가 테스트 파일 하나만 지정했더라도 프로젝트의 테스트 명령(`pytest`, `npm test`, `cargo test` 등 저장소가 쓰는 것)을 실행하라. 태스크의 범위 서술은 산출물을 한정하지 검증을 한정하지 않는다. 그 실행에서 나온 실패는 **내가 만들지 않은 것이라도** 이름을 붙여 보고에 넣는다. 스쳐 지나간 red 테스트를 언급하지 않은 보고는 누락에 의한 허위 보고다.

### REFACTOR — 정리

green 이후에만:
- 중복 제거
- 이름 개선
- 헬퍼 추출

테스트는 green으로 유지한다. 동작을 추가하지 않는다.

### 반복

다음 기능을 위한 다음 실패 테스트로.

## 좋은 테스트

| 성질 | 좋음 | 나쁨 |
|---|---|---|
| **최소** | 한 가지만. 이름에 "and"가 있으면 쪼개라. | `test('validates email and domain and whitespace')` |
| **명확** | 이름이 동작을 설명 | `test('test1')` |
| **의도를 보여줌** | 원하는 API를 시연 | 코드가 무엇을 해야 하는지 흐림 |

테스트를 쓰거나 바꿀 때는 [writing-good-tests.md](../../../skills/test-driven-development/writing-good-tests.md)(원문)를 읽는다. 테스트를 정직하게 유지하는 규칙:
- 테스트를 쓰기 **전에**, 어떤 프로덕션 변경이 이 테스트를 실패시킬지 말해본다
- 목의 동작이 아니라 실제 동작에 단언한다
- 테스트 전용 코드는 프로덕션 클래스가 아니라 테스트 유틸리티에 둔다
- 의존성을 목으로 만들기 전에 그 부수효과를 이해한다

## 흔한 합리화

| 변명 | 실제 |
|---|---|
| "테스트하기엔 너무 단순해" | 단순한 코드도 깨진다. 테스트는 30초면 된다. |
| "나중에 테스트할게" | 나중에 쓴 테스트는 바로 통과한다 — 아무것도 증명하지 못한다. 엉뚱한 것을 검사하거나, 동작 대신 구현을 검사하거나, 잊어버린 엣지 케이스를 놓칠 수 있다. 실패를 본 적이 없으니 그 테스트가 버그를 잡을 수 있다는 증거가 없다. 테스트 우선이 그 실패를 강제한다. |
| "나중 테스트도 같은 목표를 달성해 (의식이 아니라 정신이 중요)" | 나중 테스트는 "이게 무엇을 하는가?"에 답하고, 먼저 쓴 테스트는 "이게 무엇을 해야 하는가?"에 답한다. 나중에 쓴 테스트는 이미 쓴 코드에 편향된다 — 기억나는 케이스만 검증하지, 발견했을 케이스는 검증하지 않는다. |
| "이미 수동으로 테스트했어" | 수동 테스트는 임기응변이다. 무엇을 커버했는지 기록이 없고, 코드가 바뀌면 다시 돌릴 방법이 없고, 압박 속에서 케이스를 잊기 쉽다. "해봤을 때 됐어" ≠ 포괄적. |
| "X시간 작업을 지우는 건 낭비야" | 매몰비용 오류 — 그 시간은 어느 쪽이든 이미 썼다. 실제 선택지는 TDD로 다시 쓰기(높은 확신) vs 그대로 두고 테스트를 덧붙이기(낮은 확신, 버그 가능성). 신뢰할 수 없는 코드를 유지하는 것이 낭비다. |
| "참고용으로 두고 테스트를 먼저 쓸게" | 그것을 각색하게 된다. 그게 나중 테스트다. 삭제는 삭제다. |
| "먼저 탐색이 필요해" | 좋다. 탐색은 버리고 TDD로 시작하라. |
| "테스트가 어렵다 = 설계가 불명확" | 테스트의 말을 들어라. 테스트하기 어려우면 쓰기도 어렵다. |
| "TDD가 나를 느리게 할 거야" | TDD가 실용적인 길이다: 커밋 전에 버그를 잡고, 회귀를 막고, 두려움 없이 리팩터링하게 해준다. "실용적" 지름길은 프로덕션에서 디버깅하게 만든다 — 더 느리다. |
| "수동 테스트가 빨라" | 수동은 엣지 케이스를 증명하지 못한다. 변경마다 다시 테스트하게 된다. |
| "기존 코드에 테스트가 없어" | 네가 개선하는 중이다. 기존 코드에도 테스트를 추가하라. |

## 위험 신호 — 멈추고 처음부터

- 테스트 전에 코드
- 구현 후에 테스트
- 테스트가 즉시 통과
- 테스트가 왜 실패했는지 설명 못 함
- 테스트를 "나중에" 추가
- "이번 한 번만" 합리화
- "이미 수동으로 테스트했어"
- "나중 테스트도 같은 목적을 달성해"
- "의식이 아니라 정신의 문제야"
- "참고용으로 두기" 또는 "기존 코드 각색하기"
- "이미 X시간 썼는데 지우는 건 낭비야"
- "TDD는 교조적이야, 나는 실용적인 거야"
- "이건 다른 경우인데..."

**전부 같은 뜻이다: 코드를 지워라. TDD로 다시 시작하라.**

## 검증 체크리스트

작업을 완료로 표시하기 전에:

- [ ] 새 함수/메서드마다 테스트가 있다
- [ ] 구현 전에 각 테스트가 실패하는 것을 지켜봤다
- [ ] 각 테스트가 예상한 이유로 실패했다 (오타가 아니라 기능 부재)
- [ ] 각 테스트를 통과시킬 최소 코드를 썼다
- [ ] 모든 테스트가 통과한다
- [ ] 출력이 깨끗하다 (에러·경고 없음)
- [ ] 테스트가 실제 코드를 쓴다 (목은 불가피할 때만)
- [ ] 엣지 케이스와 에러가 커버된다

전부 체크할 수 없다면 TDD를 건너뛴 것이다. 처음부터 다시.

## 막혔을 때

| 문제 | 해결 |
|---|---|
| 어떻게 테스트할지 모르겠다 | 바라는 API를 써본다. 단언부터 쓴다. 사람 파트너에게 묻는다. |
| 테스트가 너무 복잡하다 | 설계가 너무 복잡한 것이다. 인터페이스를 단순화하라. |
| 전부 목으로 만들어야 한다 | 코드 결합도가 너무 높다. 의존성 주입을 쓰라. |
| 테스트 셋업이 거대하다 | 헬퍼를 추출하라. 그래도 복잡하면 설계를 단순화하라. |

## 디버깅과의 연결

버그를 찾았는가? 그것을 재현하는 실패 테스트를 쓴다. TDD 사이클을 따른다. 그 테스트가 수정을 증명하고 회귀를 막는다.

테스트 없이 버그를 고치지 않는다.

## 최종 규칙

```
프로덕션 코드 → 테스트가 존재하고 먼저 실패했다
그 외 → TDD가 아니다
```

사람 파트너의 허락 없이는 예외가 없다.
