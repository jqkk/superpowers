# dispatching-parallel-agents — 병렬 에이전트 파견

> 원문: [`skills/dispatching-parallel-agents/SKILL.md`](../../../skills/dispatching-parallel-agents/SKILL.md)
> 트리거(원문 유지): `Use when facing 2+ independent tasks that can be worked on without shared state or sequential dependencies`
> 이 문서는 사람이 읽기 위한 번역본입니다. 에이전트가 따르는 정본은 영어 원문입니다.

---

## 개요

격리된 컨텍스트를 가진 전문 에이전트에게 작업을 위임한다. 지시와 컨텍스트를 정밀하게 구성함으로써 그들이 집중을 유지하고 성공하게 만든다. 그들은 내 세션의 컨텍스트나 히스토리를 절대 상속받지 않는다 — 그들에게 필요한 것을 내가 정확히 구성해 준다. 이것은 내 컨텍스트도 조정 작업용으로 보존해 준다.

서로 무관한 실패가 여러 개(다른 테스트 파일, 다른 서브시스템, 다른 버그) 있을 때 순차적으로 조사하면 시간을 낭비한다. 각 조사는 독립적이고 병렬로 일어날 수 있다.

**핵심 원칙:** 독립적인 문제 영역마다 에이전트 하나를 파견한다. 동시에 일하게 둔다.

## 언제 쓰나

```
실패가 여러 개인가?
 └─ 예 → 서로 독립적인가?
      ├─ 아니오(연관됨) → 에이전트 하나가 전부 조사
      └─ 예 → 병렬로 작업 가능한가?
           ├─ 예 → 병렬 파견
           └─ 아니오(공유 상태) → 순차 에이전트
```

**쓸 때:**
- 근본 원인이 서로 다른 테스트 파일 3개 이상이 실패
- 여러 서브시스템이 독립적으로 깨짐
- 각 문제를 다른 문제의 맥락 없이 이해할 수 있음
- 조사들 사이에 공유 상태가 없음

**쓰지 말 것:**
- 실패들이 연관됨 (하나를 고치면 다른 것도 고쳐질 수 있음)
- 전체 시스템 상태를 이해해야 함
- 에이전트들이 서로 간섭할 것 같음

## 패턴

### 1. 독립적인 영역을 식별한다

무엇이 깨졌는지로 실패를 묶는다:
- 파일 A 테스트: 도구 승인 흐름
- 파일 B 테스트: 배치 완료 동작
- 파일 C 테스트: 중단(abort) 기능

각 영역은 독립적이다 — 도구 승인을 고치는 것이 중단 테스트에 영향을 주지 않는다.

### 2. 집중된 에이전트 작업을 만든다

각 에이전트가 받는 것:
- **구체적 범위:** 테스트 파일 하나 또는 서브시스템 하나
- **명확한 목표:** 이 테스트들을 통과시켜라
- **제약:** 다른 코드를 바꾸지 마라
- **기대 출력:** 무엇을 발견하고 무엇을 고쳤는지 요약

### 3. 병렬로 파견한다

세 개의 서브에이전트 파견을 **같은 응답 안에서** 발행한다 — 그러면 병렬로 돈다:

```text
Subagent (general-purpose): "Fix agent-tool-abort.test.ts failures"
Subagent (general-purpose): "Fix batch-completion-behavior.test.ts failures"
Subagent (general-purpose): "Fix tool-approval-race-conditions.test.ts failures"
# 셋이 동시에 돈다.
```

**한 응답에 여러 파견 호출 = 병렬 실행. 응답당 하나 = 순차.**

### 4. 검토하고 통합한다

에이전트들이 돌아오면:
- 각 요약을 읽는다
- 수정들이 충돌하지 않는지 확인한다
- 전체 테스트 스위트를 돌린다
- 모든 변경을 통합한다

## 에이전트 프롬프트 구조

좋은 에이전트 프롬프트는:
1. **집중되어 있다** — 명확한 문제 영역 하나
2. **자족적이다** — 문제를 이해하는 데 필요한 모든 컨텍스트
3. **출력이 구체적이다** — 에이전트가 무엇을 반환해야 하는가?

```markdown
src/agents/agent-tool-abort.test.ts의 실패하는 테스트 3개를 고쳐라:

1. "should abort tool with partial output capture" - 메시지에 'interrupted at' 기대
2. "should handle mixed completed and aborted tools" - 빠른 도구가 완료 대신 중단됨
3. "should properly track pendingToolCount" - 결과 3개 기대했으나 0개

타이밍/경쟁 상태 문제다. 네 작업:

1. 테스트 파일을 읽고 각 테스트가 무엇을 검증하는지 이해하라
2. 근본 원인을 식별하라 — 타이밍 문제인가 실제 버그인가?
3. 다음으로 고쳐라:
   - 임의의 타임아웃을 이벤트 기반 대기로 교체
   - 중단 구현에 버그가 있으면 수정
   - 동작이 바뀐 것을 테스트한다면 테스트 기대치 조정

단순히 타임아웃을 늘리지 마라 — 진짜 원인을 찾아라.

반환: 무엇을 발견하고 무엇을 고쳤는지 요약.
```

## 흔한 실수

**❌ 너무 넓음:** "모든 테스트를 고쳐라" — 에이전트가 길을 잃는다
**✅ 구체적:** "agent-tool-abort.test.ts를 고쳐라" — 집중된 범위

**❌ 컨텍스트 없음:** "경쟁 상태를 고쳐라" — 에이전트가 어디인지 모른다
**✅ 컨텍스트:** 에러 메시지와 테스트 이름을 붙여준다

**❌ 제약 없음:** 에이전트가 전부 리팩터링할 수 있다
**✅ 제약:** "프로덕션 코드를 바꾸지 마라" 또는 "테스트만 고쳐라"

**❌ 모호한 출력:** "고쳐라" — 무엇이 바뀌었는지 모른다
**✅ 구체적:** "근본 원인과 변경 사항 요약을 반환하라"

## 언제 쓰지 말아야 하나

**연관된 실패:** 하나를 고치면 다른 것도 고쳐질 수 있다 — 먼저 함께 조사하라
**전체 맥락이 필요:** 이해하려면 시스템 전체를 봐야 한다
**탐색적 디버깅:** 아직 무엇이 깨졌는지 모른다
**공유 상태:** 에이전트들이 간섭한다 (같은 파일 편집, 같은 리소스 사용)

## 실제 세션 사례

**상황:** 대규모 리팩터링 후 파일 3개에 걸쳐 테스트 6건 실패

**실패:**
- agent-tool-abort.test.ts: 3건 (타이밍 문제)
- batch-completion-behavior.test.ts: 2건 (도구가 실행되지 않음)
- tool-approval-race-conditions.test.ts: 1건 (실행 횟수 = 0)

**판단:** 독립적인 영역 — 중단 로직, 배치 완료, 경쟁 상태가 서로 분리됨

**파견:**
```
에이전트 1 → agent-tool-abort.test.ts 수정
에이전트 2 → batch-completion-behavior.test.ts 수정
에이전트 3 → tool-approval-race-conditions.test.ts 수정
```

**결과:**
- 에이전트 1: 타임아웃을 이벤트 기반 대기로 교체
- 에이전트 2: 이벤트 구조 버그 수정 (threadId가 잘못된 위치에 있었음)
- 에이전트 3: 비동기 도구 실행 완료 대기 추가

**통합:** 모든 수정이 독립적, 충돌 없음, 전체 스위트 green

## 검증

에이전트들이 돌아온 뒤:
1. **각 요약을 검토** — 무엇이 바뀌었는지 이해한다
2. **충돌 확인** — 에이전트들이 같은 코드를 편집했는가?
3. **전체 스위트 실행** — 모든 수정이 함께 동작하는지 확인
4. **스팟 체크** — 에이전트는 체계적인 실수를 할 수 있다
